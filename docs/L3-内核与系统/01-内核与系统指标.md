# 内核与系统指标：边界代价与恢复时间

> **这一层在讲什么。** [00-内核与系统](00-内核与系统.md) 讲清楚了内核与驱动的六项职责、UAPI 形态选型、以及 IOMMU 与虚拟化的隔离逻辑；这篇回答**怎么量这一层的代价**。
>
> **读法。** 只想知道"概念"，读完 00 就够；要定位"性能为什么掉"、或者评估内核路径是不是瓶颈，再往下读这篇。
>
> **这一层的指标特点**：它们大多是**跨越边界的固定代价**（一次系统调用、一次中断、一次缺页、一次映射）。固定代价本身不重要，**重要的是它有没有被摊薄**——所以这一层的指标几乎都要配一个"频次"来看。

---

## 一、先分清三种时间，否则一定误判

测这一层的延迟时，最容易犯的错是把三种完全不同的时间混成一个数：

| 时间 | 含义 | 谁来测 |
|---|---|---|
| **设备侧时间** | 设备从收到命令到完成实际工作 | 设备侧时间戳 / 硬件计数器 |
| **通知路径时间** | 从设备完成到软件知道（中断投递 + 处理） | 内核追踪（ftrace / 时间线） |
| **内核/驱动处理时间** | 驱动在中断或调用上下文里做的记账、唤醒工作 | 内核追踪 |

**为什么要分开**：三者优化手段完全不同。

- 设备侧慢 → 是算力/访存问题，去 [L5](../L5-编译器与算子/01-编译与算子指标.md) 看；
- 通知路径慢 → 中断聚合配置、中断亲和性（哪个核处理）、是否被别的中断挤占；
- 驱动处理慢 → 锁竞争、队列记账逻辑、批量策略。

**一个常见误判**：看到"完成延迟 50 µs"就以为是内核慢，其实可能其中 45 µs 是设备真的在算。**所以必须用硬件时间戳把设备侧和主机侧对齐**，只靠主机侧打点分不出来。

## 二、中断与完成：延迟与聚合度

| 指标 | 定义 | 权衡 |
|---|---|---|
| **中断投递延迟** | 设备触发到处理函数开始执行 | 受中断屏蔽、更高优先级中断、电源状态影响 |
| **中断处理时长** | 处理函数占用 CPU 的时间 | 太长会挤占业务线程，所以分上下半部 |
| **中断聚合度** | 一次通知覆盖了多少个完成事件 | **聚合度越高 CPU 开销越低，但单事件可见延迟越大** |
| **中断/CPU 分布** | 多队列的中断是否分散到多个核 | 全挤在一个核上会成为瓶颈 |

**聚合度是这一层最典型的取舍**：设备完成 100 个任务，是发 100 次中断，还是攒够 N 个发一次（或超时后必发）？

```
聚合度低 → 及时性好，但 CPU 被中断淹没
聚合度高 → CPU 轻松，但单次完成的可见延迟变大
超时兜底 → 避免"等不满 N 个就永远不通知"
```

所以看到"完成延迟"这个数字时，**必须问清楚聚合参数是什么**——同一个设备在不同聚合配置下可以差出数量级。

## 三、doorbell 与提交：要测的是往返，不是写入

doorbell 是"通知设备有新命令"的轻量写操作。它有两个特点：

1. **写入是"发了就算"**（posted write），设备侧不会立即回应，所以**单独测写入本身没有意义**；
2. 真正有意义的是**往返时间**：从通知发出，到设备完成并回一个完成通知。

```
doorbell 往返 = 通知写入 + 设备取指/执行 + 完成通知 + 中断处理
```

**这一层的优化方向不是"把写入弄更快"，而是"减少通知次数"**：

- **批处理**：攒一批命令再敲一次门（[L4](../L4-用户态运行时/00-用户态运行时.md) 里"doorbell 覆盖量"说的就是这个）；
- **合并完成**：把多个完成合并成一次通知（就是上一节的聚合度）；
- **避免无谓的往返**：能异步的不要同步等。

**判断信号**：如果按"每次通知覆盖的工作量"算出来的开销占比很高，说明批处理不足，而不是硬件慢。

## 四、系统调用开锁：怎么测才算准

系统调用是用户态与内核态之间最基本的边界代价。测法要注意两点：

```
方法：循环调用一个"什么都不做"的系统调用（或尽可能空的操作），测总时间
     单次开销 ≈ 总时间 / 次数

要点一：必须减去测量循环本身的开销（用户态循环也要时间）
要点二：区分"纯切换开销"与"这次调用实际做的事"
```

**更值得注意的是它怎么被摊薄**：

- 如果每个工作单元都要一次系统调用，那这部分开销会直接叠加到每个单元上；
- 这正是 [L4](../L4-用户态运行时/00-用户态运行时.md) 强调"把高频操作留在用户态"的原因——**队列在用户态内存里，就是为了避免每次提交都跨越这条边界**。

**一个量级感受**：系统调用在百纳秒到微秒级。听起来很小，但如果每次任务只跑几微秒，它就成了主要成本。

## 五、IOMMU：三类代价，别混为一谈

给设备加地址翻译层是有成本的，但成本有三种，量级差很多：

| 代价 | 何时发生 | 特点 |
|---|---|---|
| **翻译命中** | 每次 DMA 访问，且页表项在缓存里 | 很小；但**访问模式差会降低命中率** |
| **翻译未命中** | 页表项不在缓存里，需要查内存 | 中等；取决于页表层级与访问局部性 |
| **缺页处理** | 访问的地址根本没有映射 | **最贵**：要陷入、要搬运、要重试 |

**第三类最容易失控**，因为它可能是隐式发生的（就是 [L4 提到的按需迁移抖动](../L4-用户态运行时/01-运行时指标.md)）。诊断信号很直接：

```
缺页次数 × 每次缺页的搬运量  →  如果这个乘积远大于"实际参与计算的字节数"，
                                 说明数据在反复搬家，而不是在用
```

**翻译层不是纯成本**：它换来隔离与灵活布局（物理页可以不连续）。所以评估它要连收益一起看——**衡量方式是"因为不连续而避免的内存浪费"对比"翻译开销"**，而不是单看开销。

**缓存与 TLB 大小是硬件决定的**，所以能优化的是**访问局部性**：让设备在一段时间内集中访问同一个地址区间（这正是 tiling 的副产品，见 [L5](../L5-编译器与算子/00-编译器与算子.md)）。

## 六、队列吞吐：两个约束一起看

```
队列吞吐（IOPS）= min( 提交路径能喂多快 , 队列能缓冲多深 , 设备能消费多快 )
```

三个约束分别对应三层：

| 约束 | 属于哪层 | 怎么判断 |
|---|---|---|
| 提交路径喂不够 | L4/L3 | 提交开销 ÷ 单任务时间偏高 |
| 队列太浅 | L2/L3 | 设备频繁空转（队列见底） |
| 设备消费不完 | L1/L2 | 队列持续满，设备利用率已饱和 |

**队列深度的定量要求可以用 Little's law 反推**（见 [L4](../L4-用户态运行时/01-运行时指标.md)）：队列至少要能缓冲"设备吞吐 × 单任务延迟"这么多在制品，否则设备会断粮。

**一个容易忽略的点**：**队列深度是共享资源**。多进程/多虚拟机时，某个使用者把队列占满会影响其他人——这就是为什么虚拟化场景下需要配额与抢占（[L3 00](00-内核与系统.md) 里说的调度职责）。

## 七、复位与恢复：最坏情况指标

这一层的可靠性指标和别处不同——**关心的是最坏情况和恢复过程**，不是平均值：

| 指标 | 含义 |
|---|---|
| **错误检测到上报的时间** | 从设备出错到软件知道（AER 等机制） |
| **复位耗时** | 函数级复位把设备打回初始状态要多久 |
| **状态重建时间** | 复位后重新初始化 + 恢复上下文要多久 |
| **MTTR（平均恢复时间）** | 上面几项之和，加上人工介入时间 |

**为什么这个指标在集群尺度上极其重要**：卡越多，故障越频繁。所以 [L7 把 MTTR 列为四个关键指标之一](../L7-分布式与集群/01-集群评测.md)——一个集群的"有效训练时间占比"很大程度上由这一层决定。

**它也会反过来影响上层设计**：[L4 的错误模型](../L4-用户态运行时/00-用户态运行时.md)之所以选择"上下文可丢弃、重建即可"，前提是**这一层的重建路径足够快、足够可靠**。所以 checkpoint 的频率、恢复的自动化程度，都是这两层共同决定的。

## 八、怎么评测才算可信

**必须固定的**：内核版本与配置（含 IOMMU 开关）、驱动版本、中断聚合参数与亲和性设置、是否开启了调试追踪（追踪本身有开销）、以及设备的电源/频率状态。

**必须报告的**：设备侧与主机侧时间**分开**、中断聚合参数、是否区分冷/热路径、以及复位/恢复是"测试环境"还是"真实故障"。

**这一层特有的坑**：

- **把设备时间算成内核时间**：不用硬件时间戳就无法区分（第一节）。
- **不区分冷路径与热路径**：首次映射、首次缺页、首次注册的开销比稳态大得多，混在一起会失真。
- **忽略中断亲和性**：所有中断落在一个核上时，测出来的是那个核的能力，不是系统的能力。
- **在开着追踪的情况下测延迟**：追踪框架本身会改变时序，必须给出开/关对比。
- **用平均值掩盖尾部**：这一层的尾部（缺页、复位）才是决定体验的部分。
- **忽略锁竞争**：多进程/多队列场景下，驱动内部的锁会成为瓶颈，单进程测试看不出来。
- **把"恢复成功"当"恢复完成"**：要测到状态真的恢复可用，而不是复位命令返回了就算。

## 九、一张表：该看哪个指标

| 你要回答的问题 | 该看的指标 |
|---|---|
| 完成通知为什么慢 | 中断投递延迟 + 聚合参数（区分设备侧与主机侧时间） |
| 提交是不是瓶颈 | doorbell 往返 ÷ 单次通知覆盖的工作量 |
| 边界代价高不高 | 单次系统调用开销 ÷ 每次调用覆盖的工作量 |
| DMA 有没有抖动 | 缺页次数 × 每次搬运量 vs 实际参与计算的字节数 |
| 队列为什么喂不满 | 三个约束分别排查（提交路径 / 队列深度 / 设备消费） |
| 多租户为什么互相影响 | 中断与队列的分配、驱动内锁竞争、配额设置 |
| 系统能不能扛住故障 | 复位耗时 + 状态重建时间 + MTTR |
| 结果可信吗 | 冷/热路径是否分开 + 追踪是否影响测量 + 亲和性是否固定 |
