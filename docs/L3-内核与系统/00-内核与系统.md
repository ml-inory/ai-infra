# 内核与系统：让设备成为系统的一部分

> **这一层在讲什么。** 一张卡插进机器，操作系统并不自动"认识"它。要有人负责：**认领它、给它分配地址与中断、把它安全地暴露给用户程序、在它出错时处理它**。这些事由内核与驱动完成——这就是 L3。
>
> **本文建立概念，不追求精确。** 想知道"一次中断要多少微秒、复位要多久恢复"，看 [01-内核与系统指标](01-内核与系统指标.md)。
>
> **和上下层的关系。** 往下看，这一层要面对 L2 定下的硬件契约（寄存器、队列、doorbell）；往上看，它给 [L4 用户态运行时](../L4-用户态运行时/00-用户态运行时.md) 提供可用的对象。
>
> **这一层最重要的设计判断是"边界画在哪"**：哪些事必须留在内核（安全、隔离、初始化），哪些事可以甩给用户态（高频提交、doorbell）。这条线画错了，要么性能塌掉，要么安全性无从谈起。

---

## 一、内核到底要负责哪几件事

把"让设备能用"这件事拆开，内核与驱动承担六项职责：

| 职责 | 不做会怎样 |
|---|---|
| **发现与认领** | 没人知道总线上多了个设备，或者多个驱动抢同一个设备 |
| **资源分配** | 设备的寄存器窗口（BAR）没被映射，地址区间没被登记，中断没被分配 |
| **隔离** | 设备能读写任意内存——这在多租户环境里是灾难 |
| **暴露接口** | 用户程序没有任何合法途径去操作它 |
| **调度与多进程** | 多个进程用同一张卡时互相干扰、互相饿死 |
| **容错与恢复** | 设备挂死之后只能重启整机 |

**其中"隔离"是最容易被低估的一项。** 一个能发起 DMA 的设备，如果不加约束，理论上可以读写物理内存的任何位置。所以**给设备加地址翻译层不是可选项，而是多租户的前提**——这也是后面 IOMMU 那一节存在的原因。

## 二、设备是被"发现"和"认领"的

设备进系统的路径和普通外设一样，分三步：

```
第一步：被发现
  总线枚举（开机扫描 / 热插拔事件）→ 内核为每个设备建立数据结构
  读到的是"身份证"：厂商 ID、设备 ID、类型、能力

第二步：被认领（匹配）
  每个驱动声明"我支持哪些 ID"
  总线把设备和驱动对上号 → 调用驱动的 probe

第三步：被初始化
  probe 里完成：使能设备、申请地址窗口、映射寄存器、申请中断、注册对外接口
```

**关键设计是"设备客观存在，驱动后来才加载"**——两者通过总线自动匹配，而不是写死绑定。这样：

- 驱动可以后加载（模块按需插入），设备一旦出现就会被认领；
- 设备可以热插拔，驱动要能处理"随时来、随时走"；
- 同一个设备可能被多个驱动支持，靠匹配规则的优先级决定谁赢。

**probe 里做的事必须能"反着做回去"**，因为每一步都可能失败：

```
使能设备 → 申请地址区间 → 映射寄存器 → 申请中断 → 注册对外接口
   ↑ 任何一步失败，都要把前面申请到的资源按相反顺序释放
```

这个"失败回滚"是驱动最常出错的地方，也是为什么现代内核提供**资源托管机制**（`devm_*` 系列）——它把资源绑到设备生命周期上，释放顺序由框架负责，而不是靠人记得写对 goto 链。

### 中断：设备通知主机的两条路

设备算完了要告诉主机，机制上分两代：

| 机制 | 特点 |
|---|---|
| **传统中断（INTx）** | 共享中断线，多个设备可能共用一条，需要驱动自己判断"是不是我" |
| **MSI / MSI-X** | 设备直接写一个特定地址来触发中断，**不共享、可定向、支持多向量** |

MSI-X 的"多向量"很关键：**一条中断对应一个队列**，这样多队列设备可以让不同队列的中断落到不同 CPU 核上，避免所有中断都挤在一个核。**中断聚合（把多次完成合并成一次通知）也是在这一层配置的**——它在"及时性"和"开销"之间取平衡。

中断处理本身通常分两半：**上半部**只做最紧急的事（快速响应、清中断），**下半部**（含线程化中断）做耗时的处理。原因是中断上下文里不能睡眠、不能做长时间工作。

## 三、UAPI 形态：这一层最重要的选型

设备最终要以某种"文件接口"的形式暴露给用户程序。**选哪种形态，决定了上层能做什么、以及将来的可扩展性**。四种主流形态：

| 形态 | 面向场景 | 特点 |
|---|---|---|
| **字符设备（char device）** | 单设备单节点、接口简单 | 最直接：用户 `open` 一个节点，通过 `read`/`write`/`ioctl`/`mmap` 操作。样板代码少，但**所有语义要自己定义** |
| **DRM 的 accel 子系统** | 计算加速器 | 借用 DRM（显示子系统）多年积累的基础设施：设备管理、内存管理、统一的任务提交与调度框架。**适合"按加速器来用"而不是"按显卡来用"** |
| **VFIO mdev** | 虚拟化 / 多租户 | 把**一个物理设备的能力切分**给多个消费者（典型是多个虚拟机），由内核中介每一次访问。隔离性最强，代价是有中介开销 |
| **dma-buf** | 跨驱动共享缓冲区 | 不暴露设备本身，而是暴露**一块可共享的内存**，让不同设备/驱动零拷贝地共用它（对应 [L4 的零拷贝](../L4-用户态运行时/00-用户态运行时.md)） |

**怎么选，看三个问题**：

1. **要不要给虚拟机用？** 要 → VFIO 系（直通或 mdev）。
2. **主要是"算"还是"显示"？** 算 → 考虑 accel 子系统，能复用现成的调度与内存框架；只是要个控制通道 → 字符设备就够。
3. **数据要不要跨设备流转？** 要 → 无论如何都要支持 dma-buf，它是共享的标准做法。

> **一个实务观察**：这四种形态**不是互斥的**。一个成熟的加速器驱动常常同时提供：字符设备或 accel 节点给本机进程用、dma-buf 导出内存给别的设备用、VFIO 路径给虚拟机用。**选型不是选一个，而是决定"先做哪个、后补哪个"**。

## 四、内存与地址空间：隔离与共享的博弈

### 4.1 IOMMU：给设备加一层地址翻译

设备发起 DMA 时用的是"设备地址"。如果没有翻译层，这个地址就是物理地址——**设备能写到哪，完全取决于它自己**。IOMMU（ARM 体系里对应 SMMU）做的事就是**在设备和物理内存之间插一层页表**：

```
设备发出的地址  →  IOMMU 查页表  →  物理地址
                      ↓
              不在映射里？→ 拦截（缺页或报错）
```

这带来三个收益：

1. **隔离**：设备只能访问被明确映射给它的内存，越界会被拦下；
2. **地址空间自由**：设备看到的是连续的虚拟地址，物理页可以不连续（大块内存不再需要连续物理页）；
3. **支持虚拟化**：把设备地址翻译到某个虚拟机的地址空间里，直通才有可能。

**代价是每次翻译都要查表**（靠缓存缓解），以及**缺页处理会引入延迟**。

### 4.2 PASID 与 SVA：让设备用进程自己的页表

上面说的翻译是"设备级"的——整个设备一张页表。但多进程共享一张卡时，不同进程有各自的地址空间，于是需要更细的粒度：

- **PASID**（Process Address Space ID）：给设备发起的每次访问带上一个"这是哪个进程"的标识，让 IOMMU 能按进程选页表。
- **SVA**（Shared Virtual Addressing）：进一步让**设备直接使用进程的页表**，于是用户态指针可以不经转换直接传给设备。

**这两个机制的意义是消除"指针翻译"这一层抽象税**：没有 SVA 时，用户态指针和设备能用的地址是两套体系，中间要做锁定、翻译、映射；有了 SVA，设备访问内存就像 CPU 一样。

### 4.3 pin 与迁移：一个根本的取舍

设备要被允许访问某块内存，通常需要保证这块内存**不会被换出或移动**——这就是 **pin（钉住）**。围绕它有一个根本取舍：

| 做法 | 好处 | 代价 |
|---|---|---|
| **显式 pin + 显式拷贝** | 行为可预测、延迟稳定、实现简单 | 灵活性差；设备能用的内存受限于已 pin 的部分；大模型场景下 pin 大量内存会挤压系统 |
| **可迁移内存 + 设备缺页** | 编程简单；数据按需流动；显存不够也能跑 | 迁移是隐式的，访问模式不好就抖动；缺页处理路径复杂（要能在缺页时安全地进入驱动） |

**这个取舍会一路影响到最上层**：[L4](../L4-用户态运行时/00-用户态运行时.md) 里"按需迁移的收益与风险"、[L6](../L6-框架与模型/00-框架与模型.md) 里"显存不够怎么办"，根源都在这一层选择了哪条路。

**缺少页/迁移的场景需要一套专门的框架**：允许设备在访问到未映射页时触发一次"设备缺页"，由内核协调把页搬过来再重试。这条路径比 CPU 缺页复杂得多，因为它要和设备的状态机配合。

## 五、虚拟化与多租户

让多个使用者共享一张卡，有三种粒度递增的方案：

| 方案 | 做法 | 隔离强度 |
|---|---|---|
| **时间片共享** | 一个驱动实例，多个进程轮流用 | 最弱：靠驱动自己保证公平与安全 |
| **SR-IOV（硬件切分）** | 硬件把设备切成多个"虚拟功能"（VF），每个可独立分配 | 强：硬件级隔离，VF 可直通给虚拟机 |
| **软件中介（mdev）** | 由内核把一次物理设备的能力**切分并中介**给多个消费者 | 最强（每次访问都过中介），但有中介开销 |

**SR-IOV 的核心概念**是：物理功能（PF）负责管理与配置，虚拟功能（VF）是轻量的、可独立分配给虚拟机使用。它的优势是**VF 直通几乎无性能损失**，代价是**硬件必须支持、且切分粒度由硬件固定**。

**mdev 的价值在于"硬件不支持 SR-IOV 时也能切分"**——它用软件把设备能力虚拟化出来，代价是每次访问都要经过中介。

## 六、可靠性：设备会坏，而且会挂死

加速卡是高功耗、高复杂度的设备，故障是常态。这一层要处理三类问题：

1. **可纠正/不可纠正错误**：PCIe 有一套错误报告机制（AER），能报告链路错误、畸形包等，并区分**可恢复**与**致命**。驱动可以在这条路径上记录、上报、甚至尝试恢复。
2. **设备挂死与复位**：设备可能进入无法响应的状态。这时需要**函数级复位（FLR）**——只复位这一个设备，而不是重启整机。它是"设备级恢复"的硬件基础。
3. **恢复后的状态重建**：复位把设备打回初始状态，**驱动必须重新走一遍初始化并把上下文恢复回来**。对上层来说，这对应 [L4 的错误模型](../L4-用户态运行时/00-用户态运行时.md)——上下文可能整体失效，恢复策略是"重建"而不是"修复现场"。

**错误注入是这一层很重要的工程实践**：主动制造错误（链路错误、超时、复位），验证恢复路径真的能工作。没有错误注入，恢复代码基本等于没测过。

## 七、这一层与 L4 的边界

两者容易混淆，边界可以这样记：

| | L3 内核与系统 | L4 用户态运行时 |
|---|---|---|
| **典型动作** | 枚举、probe、映射、隔离、复位 | 提交、doorbell、事件同步、内存池 |
| **频率** | 低频（初始化、错误处理） | 高频（每次 launch） |
| **优化目标** | 正确性、隔离、可恢复 | 延迟、吞吐 |
| **出错后果** | 系统级（内核崩溃、安全边界失守） | 进程级（上下文失效） |

**一句话**：**L3 负责"设备可以被安全地用"，L4 负责"设备可以被快速地用"。** 热门路径（提交）被有意放到用户态，而冷路径（映射、隔离、复位）留在内核——这个分工正是 [overview.md](../overview.md) 里"压控制/同步税"的具体形式。
