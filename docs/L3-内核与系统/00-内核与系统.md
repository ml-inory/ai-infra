# 内核与系统：让设备成为系统的一部分

> **这一层在讲什么。** 一张卡插进机器，操作系统并不自动"认识"它。要有人负责：**认领它、给它分配地址与中断、把它安全地暴露给用户程序、在它出错时处理它**。这些事由内核与驱动完成——这就是 L3。
>
> **本文建立概念，不追求精确。** 想知道"一次中断要多少微秒、复位要多久恢复"，看 [01-内核与系统指标](01-内核与系统指标.md)。
>
> **和上下层的关系。** 往下看，这一层要面对 L2 定下的硬件契约（寄存器、队列、doorbell）；往上看，它给 [L4 用户态运行时](../L4-用户态运行时/00-用户态运行时.md) 提供可用的对象。
>
> **这一层最重要的设计判断是"边界画在哪"**：哪些事必须留在内核（安全、隔离、初始化），哪些事可以甩给用户态（高频提交、doorbell）。这条线画错了，要么性能塌掉，要么安全性无从谈起。

## 一、内核到底要负责哪几件事

把"让设备能用"这件事拆开，内核与驱动承担六项职责：

| 职责 | 不做会怎样 |
|---|---|
| **发现与认领** | 没人知道总线上多了个设备，或者多个驱动抢同一个设备 |
| **资源分配** | 设备的寄存器窗口（BAR）没被映射，地址区间没被登记，中断没被分配 |
| **隔离** | 设备能读写任意内存——这在多租户环境里是灾难 |
| **暴露接口** | 用户程序没有任何合法途径去操作它 |
| **调度与多进程** | 多个进程用同一张卡时互相干扰、互相饿死 |
| **容错与恢复** | 设备挂死之后只能重启整机 |

**其中"隔离"是最容易被低估的一项。** 一个能发起 DMA 的设备，如果不加约束，理论上可以读写物理内存的任何位置。所以**给设备加地址翻译层不是可选项，而是多租户的前提**——这也是后面 IOMMU 那一节存在的原因。

### 设备"可发现性"的来源

设备为什么能被自动认出来？因为 PCIe 规定了一段**标准化的配置空间**，设备必须在这里如实报告自己的身份与需求。内核 UAPI 头文件里给出的规模是权威依据：

```
传统 PCI 与 PCI-X Mode 1 设备：256 字节配置空间
PCI-X Mode 2 与 PCIe 设备：4096 字节配置空间（扩展配置空间）
```

前 256 字节是兼容区（厂商 ID、设备 ID、类型码、六个 BAR 等），扩展部分放各种能力结构。**BAR（基址寄存器）是"可发现性"最直接的体现**：设备不告诉内核"我的寄存器在物理地址 X"，而是提供一个窗口，由系统分配地址再写回设备——**大小也是可探测的**（往寄存器写全 1 再读回，看哪些位能被解码）。

所以"可发现性"具体指三件事：**能被枚举发现、能报告自己需要什么资源、资源地址由系统分配而不是写死**。这三点在需要人工在代码里写死地址的总线（如早期的平台设备）上是没有的。

## 二、设备是被"发现"和"认领"的

设备进系统的路径和普通外设一样，分三步：

```
第一步：被发现
  总线枚举（开机扫描 / 热插拔事件）→ 内核为每个设备建立数据结构
  读到的是"身份证"：厂商 ID、设备 ID、类型、能力

第二步：被认领（匹配）
  每个驱动声明"我支持哪些 ID"
  总线把设备和驱动对上号 → 调用驱动的 probe

第三步：被初始化
  probe 里完成：使能设备、申请地址窗口、映射寄存器、申请中断、注册对外接口
```

**关键设计是"设备客观存在，驱动后来才加载"**——两者通过总线自动匹配，而不是写死绑定。这样：

- 驱动可以后加载（模块按需插入），设备一旦出现就会被认领；
- 设备可以热插拔，驱动要能处理"随时来、随时走"；
- 同一个设备可能被多个驱动支持，靠匹配规则的优先级决定谁赢。

**匹配这个动作本身有三个值得知道的机制**：

1. **匹配函数的返回值有约定**：返回正值表示"这个设备我能管"，返回 0 表示不匹配（多个驱动都会被问一遍，所以不是"第一个说不就结束"）。
2. **可以推迟探测**：如果驱动发现自己依赖的资源还没就绪（比如它依赖的另一个设备还没初始化完），可以返回一个特殊错误码表示"**稍后再试**"，内核会把设备放进延迟探测队列，而不是直接判定失败。**这解决的是"驱动加载顺序不确定"这个真问题**——但它有一条硬约束：**如果驱动已经创建了子设备，就不能再返回这个码**，否则会陷入自己的无限循环。
3. **用户可以强行指定驱动**：通过 sysfs 可以绕过总线原本的匹配规则，把某个设备绑定到指定驱动。**这是调试与救急手段**——当匹配规则出错、或者需要临时用另一个驱动接管设备时非常有用。

> 一个容易混淆的细节：**"remove 的返回值"在不同层级并不一致**——设备驱动层的 `remove` 返回 `int`，而总线层与 PCI 驱动层的 `remove` 返回 `void`。写驱动时要按实际接口来，不能一概而论。

**probe 里做的事必须能"反着做回去"**，因为每一步都可能失败：

```
使能设备 → 申请地址区间 → 映射寄存器 → 申请中断 → 注册对外接口
   ↑ 任何一步失败，都要把前面申请到的资源按相反顺序释放
```

这个"失败回滚"是驱动最常出错的地方，也是为什么现代内核提供**资源托管机制**（`devm_*` 系列）——它把资源绑到设备生命周期上，释放顺序由框架负责，而不是靠人记得写对 goto 链。

### 中断：设备通知主机的两条路

设备算完了要告诉主机，机制上分两代：

| 机制 | 特点 |
|---|---|
| **传统中断（INTx）** | 共享中断线，多个设备可能共用一条，需要驱动自己判断"是不是我" |
| **MSI** | 设备向一个特定地址写入来触发中断；**从不共享**，但向量数上限低（最多 32 个，且必须是 2 的幂、必须连续分配） |
| **MSI-X** | 同样靠写入触发，但支持 **1 到 2048 个中断**、可逐向量屏蔽，且向量地址可任意指定 |

**MSI 家族为什么优于共享中断**：除了不共享，还有一个关键的正确性好处——**中断的写入不能越过数据写入**，所以当中断到达时，数据已经在内存里了，驱动不需要再去读设备寄存器做一次 flush。

**MSI-X 的"多向量"很关键**：**一条中断对应一个队列**，这样多队列设备可以让不同队列的中断落到不同 CPU 核上，避免所有中断都挤在一个核。

内核侧的申请接口是 `pci_alloc_irq_vectors(dev, min_vecs, max_vecs, flags)`，其中 `flags` 可取 `PCI_IRQ_MSIX` / `PCI_IRQ_MSI` / `PCI_IRQ_INTX`（后者只在申请 1 个向量时合法），优先级是 MSI-X > MSI > INTx。拿到中断号要用 `pci_irq_vector()` 转换，因为 MSI-X 下它是**表项索引**、MSI 下是已启用向量的索引、INTx 下必须为 0。

> **一个容易踩的坑**：如果用了 `pcim_enable_device()` 这类托管接口，就**不要**再手工调用释放函数（如 `pci_free_irq_vectors`），否则会双重释放——释放交给资源托管机制自动做。

**中断聚合（把多次完成合并成一次通知）也是在这一层配置的**——它在"及时性"和"开销"之间取平衡。

中断处理本身通常分两半：**上半部**只做最紧急的事（快速响应、清中断），**下半部**（含线程化中断）做耗时的处理。原因是中断上下文里不能睡眠、不能做长时间工作。

> 术语说明："上半部/下半部"是驱动开发圈的通行说法，**它不是内核官方文档里的术语**——内核官方把对应概念表达为 primary handler（`handler`）与 threaded handler（`thread_fn`）两个回调。写文档时按官方术语更严谨。

## 三、UAPI 形态：这一层最重要的选型

设备最终要以某种"文件接口"的形式暴露给用户程序。**选哪种形态，决定了上层能做什么、以及将来的可扩展性**。四种主流形态：

| 形态 | 面向场景 | 特点 |
|---|---|---|
| **字符设备（char device）** | 单设备单节点、接口简单 | 最直接：用户 `open` 一个节点，通过 `read`/`write`/`ioctl`/`mmap` 操作。样板代码少，但**所有语义要自己定义** |
| **DRM 的 accel 子系统** | 计算加速器 | 借用 DRM（显示子系统）多年积累的基础设施：设备管理、内存管理、统一的任务提交与调度框架。**适合"按加速器来用"而不是"按显卡来用"** |
| **VFIO mdev** | 虚拟化 / 多租户 | 把**一个物理设备的能力切分**给多个消费者（典型是多个虚拟机），由内核中介每一次访问。隔离性最强，代价是有中介开销 |
| **dma-buf** | 跨驱动共享缓冲区 | 不暴露设备本身，而是暴露**一块可共享的内存**，让不同设备/驱动零拷贝地共用它（对应 [L4 的零拷贝](../L4-用户态运行时/00-用户态运行时.md)） |
| **UIO** | 把寄存器直接映射给用户态 | 最"放手"的一种：内核只负责映射内存与转发中断，其余全交给用户态驱动。**代价明确：没有 IOMMU 保护、中断支持有限、访问 PCI 配置空间需要 root** |

**UIO 值得单独知道，因为它划出了"放手"的边界**：官方文档明确它**不是通用驱动接口**——已经被别的子系统（网络、串口、USB）处理得不错的设备不适合它；能用 UIO 的硬件要满足：有可映射的内存、被写这块内存就能完全控制设备、通常会产生中断、且不属于任何标准内核子系统。**不满足 IOMMU 保护这一条，就决定了 UIO 不适合多租户场景**。

**怎么选，看三个问题**：

1. **要不要给虚拟机用？** 要 → VFIO 系（直通或 mdev）。
2. **主要是"算"还是"显示"？** 算 → 考虑 accel 子系统，能复用现成的调度与内存框架；只是要个控制通道 → 字符设备就够。
3. **数据要不要跨设备流转？** 要 → 无论如何都要支持 dma-buf，它是共享的标准做法。

> **一个实务观察**：这四种形态**不是互斥的**。一个成熟的加速器驱动常常同时提供：字符设备或 accel 节点给本机进程用、dma-buf 导出内存给别的设备用、VFIO 路径给虚拟机用。**选型不是选一个，而是决定"先做哪个、后补哪个"**。

## 四、内存与地址空间：隔离与共享的博弈

### 4.1 IOMMU：给设备加一层地址翻译

设备发起 DMA 时用的是"设备地址"。如果没有翻译层，这个地址就是物理地址——**设备能写到哪，完全取决于它自己**。IOMMU（ARM 体系里对应 SMMU）做的事就是**在设备和物理内存之间插一层页表**：

```
设备发出的地址  →  IOMMU 查页表  →  物理地址
                      ↓
              不在映射里？→ 拦截（缺页或报错）
```

这带来三个收益：

1. **隔离**：设备只能访问被明确映射给它的内存，越界会被拦下；
2. **地址空间自由**：设备看到的是连续的虚拟地址，物理页可以不连续（大块内存不再需要连续物理页）；
3. **支持虚拟化**：把设备地址翻译到某个虚拟机的地址空间里，直通才有可能。

**代价是每次翻译都要查表**（靠缓存缓解），以及**缺页处理会引入延迟**。

### 4.2 PASID 与 SVA：让设备用进程自己的页表

上面说的翻译是"设备级"的——整个设备一张页表。但多进程共享一张卡时，不同进程有各自的地址空间，于是需要更细的粒度：

- **PASID**（Process Address Space ID）：给设备发起的每次访问带上一个"这是哪个进程"的标识，让 IOMMU 能按进程选页表。
- **SVA**（Shared Virtual Addressing）：进一步让**设备直接使用进程的页表**，于是用户态指针可以不经转换直接传给设备。

**这两个机制的意义是消除"指针翻译"这一层抽象税**：没有 SVA 时，用户态指针和设备能用的地址是两套体系，中间要做锁定、翻译、映射；有了 SVA，设备访问内存就像 CPU 一样。

**而且 SVA 顺带解决了一个更根本的问题：它不需要 pin。** 官方文档说得直接——SVA 除了让设备能直接用应用虚拟地址，**还免去了为 DMA 钉住页面**。这一点值得展开，因为它和下一小节的取舍正好是对立的两条路：

| 路线 | 机制 | 代价 |
|---|---|---|
| **pin + 显式映射** | 把页面钉住，建立固定映射交给设备 | 简单可预测，但页面被占住、无法回收 |
| **SVA / 可重放缺页** | 设备用进程页表，缺页时通过缺页机制补上 | 无需 pin、内存可自由回收，但要硬件支持（PCIe 的 ATS 与 PRI 能力） |

官方对"哪种更好"的态度也很明确：**如果硬件支持可重放的页错误，那么完全可以不 pin，这是理想情况**。

**pin 本身也有两套 API，不能混用**（这是内核文档专门澄清的一个坑）：

- **`pin_user_pages*()`** 用于 **DMA-pinned** 页——即长期交给设备、需要防止被回收或迁移的页面；
- **`get_user_pages*()`** 用于其他场景（只短暂访问、不需要长期钉住）。

两者对页引用计数的记账方式**不同且互斥**，**混用会导致计数错误**，进而让内核在"这个页到底能不能回收"上判断失误。判断一个页是否被 DMA 钉住，有专门的查询接口供内核其它代码（如页回收路径）使用。

> 为什么这件事在本层很关键：**pin 与回收/迁移是对立的**。页面一旦被长期钉住，内存管理就失去了对它做优化的余地——这直接影响到上层"能不能把显存当缓存用""内存压力下会不会失败"。所以**是否支持 SVA，是选硬件时一个影响很深远的差异**。

### 4.3 pin 与迁移：一个根本的取舍

设备要被允许访问某块内存，通常需要保证这块内存**不会被换出或移动**——这就是 **pin（钉住）**。围绕它有一个根本取舍：

| 做法 | 好处 | 代价 |
|---|---|---|
| **显式 pin + 显式拷贝** | 行为可预测、延迟稳定、实现简单 | 灵活性差；设备能用的内存受限于已 pin 的部分；大模型场景下 pin 大量内存会挤压系统 |
| **可迁移内存 + 设备缺页** | 编程简单；数据按需流动；显存不够也能跑 | 迁移是隐式的，访问模式不好就抖动；缺页处理路径复杂（要能在缺页时安全地进入驱动） |

**这个取舍会一路影响到最上层**：[L4](../L4-用户态运行时/00-用户态运行时.md) 里"按需迁移的收益与风险"、[L6](../L6-框架与模型/00-框架与模型.md) 里"显存不够怎么办"，根源都在这一层选择了哪条路。

**缺少页/迁移的场景需要一套专门的框架**：允许设备在访问到未映射页时触发一次"设备缺页"，由内核协调把页搬过来再重试。这条路径比 CPU 缺页复杂得多，因为它要和设备的状态机配合。

## 五、虚拟化与多租户

让多个使用者共享一张卡，有三种粒度递增的方案：

| 方案 | 做法 | 隔离强度 |
|---|---|---|
| **时间片共享** | 一个驱动实例，多个进程轮流用 | 最弱：靠驱动自己保证公平与安全 |
| **SR-IOV（硬件切分）** | 硬件把设备切成多个"虚拟功能"（VF），每个可独立分配 | 强：硬件级隔离，VF 可直通给虚拟机 |
| **软件中介（mdev）** | 由内核把一次物理设备的能力**切分并中介**给多个消费者 | 最强（每次访问都过中介），但有中介开销 |

**SR-IOV 的核心概念**是：物理功能（PF）负责管理与配置，虚拟功能（VF）是轻量的、可独立分配给虚拟机使用。它的优势是**VF 直通几乎无性能损失**，代价是**硬件必须支持、且切分粒度由硬件固定**。

**mdev 的价值在于"硬件不支持 SR-IOV 时也能切分"**——它用软件把设备能力虚拟化出来，代价是每次访问都要经过中介。

> 一个状态提醒：虚拟化这条线的接口**正在换代**。新的用户态 IOMMU 接口（IOMMUFD）被定位为管理 I/O 页表的新方式，而旧的容器/组模型官方说法是"**最终打算废弃**"；但同一份文档又提醒兼容模式"功能还不完整，目前不建议切换"。**所以这属于"进行中"状态**，写选型结论时要绑定具体内核版本，不能写成"已经废弃"。
>
> 同样地，mdev 的长期去向**没有官方定论**——新接口文档里只是把 mdev 描述为新接口的一个"内核内使用者"，暗示两者**共存**而非替代。所以**不要写"mdev 已废弃"**。

## 六、调度与抢占：多进程共享一张卡

前面讲的都是"一个使用者怎么用设备"。但真实环境里多个进程（或多台虚拟机）要共享同一张卡，于是需要**调度**：谁先执行、执行多久、能否被打断。

### 6.1 内核提供的调度框架

GPU 类驱动普遍复用内核里一套通用的 GPU 调度器框架。它的结构值得记住，因为它把"公平与优先级"表达得很清楚：

```
每个硬件运行队列  ← 一个调度器
   └── 多个优先级队列（高优先硬件 / 高优先软件 / 内核 / 普通…）
         └── 若干 entity（可理解为"一个使用者/上下文"）
               └── 若干 job（严格按入队顺序执行）
```

三条要点：

1. **调度器从运行队列里按 FIFO 选择 entity**——公平性体现在 entity 之间，而不是 job 之间；
2. **entity 内部的 job 严格有序**，这保证了一个上下文的执行语义；
3. **它自带流控机制**：每个 job 带一个"信用额度"，已提交未完成的额度会被计入，超出上限就等待。**这就是防"某个使用者把设备淹没"的手段**。

**这套框架还把复位恢复纳入了设计**：它提供了"停止调度（用于复位恢复）"和"复位后恢复任务"的接口，也就是说**调度器本身就是错误恢复流程的一部分**。

> **一个术语提醒**：硬件加速器的**抢占粒度**分类在业界**没有权威统一定义**。我原来想写的"指令级 / 任务级 / 驱动级"这套三分法**在任何内核文档或规范里都找不到出处**，其中"驱动级抢占"尤其是口头说法。可核实的只有具体驱动里的枚举值（例如某驱动的补丁里给出的 `default` / `mid-thread` / `thread-group` / `command` 四档，通过写某个寄存器字段实现）。**所以讲抢占时应当描述具体实现，而不是套用一套不存在的标准分类。**

### 6.2 为什么抢占对加速卡特别难

CPU 上一个线程可以随时被换出（上下文切换有硬件支持）。加速器不一样：

- **设备上可能跑着成百上千个并行线程**，它们的状态分布在大量寄存器与片上存储里——**保存/恢复整个上下文的代价极高**；
- **一条命令内部可能已经启动了不可中断的操作**（例如一次大矩阵乘的流水线）；
- 因此抢占往往需要**分档**：粗粒度的（只在任务边界打断）实现简单但延迟大，细粒度的（能在指令间打断）响应快但硬件代价高。

**这个取舍决定了两种能力**：多租户的公平性（粗粒度够用）与低延迟推理的响应性（需要细粒度）。所以"支持抢占"这句话必须问清**是哪一档**。

## 六、可靠性：设备会坏，而且会挂死

加速卡是高功耗、高复杂度的设备，故障是常态。这一层要处理三类问题：

### 6.1 错误报告：AER 与它的分级

PCIe 有一套错误报告机制（**AER**，Advanced Error Reporting），分两级：

| 分级 | 含义 | 处理方式 |
|---|---|---|
| **可纠正错误（correctable）** | 协议层能自恢复，无数据丢失 | 记录即可，无需软件介入 |
| **不可纠正错误（uncorrectable）** | 再分两档：**non-fatal**（该事务不可靠，但链路本身完全可用）与 **fatal**（链路不可靠） | 需要软件介入恢复 |

AER 驱动只挂在**支持该能力的根端口与根复合体集成端点**上，它做三件事：收集错误信息、报告给用户、执行恢复动作。

**恢复动作有明确的优先级**：对不可纠正错误施加 **Secondary Bus Reset**（复位施加在错误源设备**之上**的那个端口）；**但如果错误源是根复合体集成端点（它上方没有端口可复位），就改用函数级复位（FLR）**。这条规则把"复位"和"设备拓扑"绑在了一起——**复位手段取决于设备挂在树的哪个位置**。

对应的 sysfs 属性可调限速（可纠正错误与致命错误默认限速，fatal 不限速），避免错误风暴把日志刷爆。

### 6.2 复位：FLR 与"需要更强复位"的情况

设备可能进入无法响应的状态，这时需要**函数级复位（FLR）**——只复位这一个设备，而不是重启整机。它是"设备级恢复"的硬件基础：设备通过能力位声明自己是否支持。

**但 FLR 不总是够用**，内核里对此有明确的表达：

- 有些设备需要**更强的复位**（fundamental reset），驱动可以在 probe 时标记这一点；
- 内核还维护一份**复位方法的优先级列表**，并按设备**排除**某些不可靠的复位手段（例如"即使设备声明支持 FLR 也不要用它"）。

**驱动与内核的复位流程之间是有契约的**：设备复位时，IOMMU 侧的映射状态也要协同处理，否则复位后的设备可能拿着旧映射去访问已经不属于它的内存。

### 6.3 恢复：设备级错误的六步流程

设备级错误恢复在内核里是一个**定义清楚的流程**，驱动通过一组回调参与（`error_detected` / `mmio_enabled` / `slot_reset` / `resume`）。要点：

- **不要求实现全部回调，但一旦实现任何一个，就必须实现 `error_detected`**——它是流程的入口；
- 驱动如果没有提供这套回调，**设备不会被恢复**，内核只会打印信息指出这是不可恢复的设备；
- 在错误检测到复位完成之间，**中断投递既不被保证也不被停止**——驱动此时收到中断应当明确"这不是我处理的"，交由平台屏蔽。

**恢复流程里最关键的一步是状态重建**：复位把设备打回初始状态，驱动必须重新初始化配置空间（内核文档明确要求用保存的状态去恢复寄存器），才能把设备从"未初始化的 D0"带回"活动的 D0"。这也解释了为什么内核在枚举时会主动保存一次配置空间状态——**就是为了给将来的错误恢复留一份可回滚的快照**。

对上层来说，这正对应 [L4 的错误模型](../L4-用户态运行时/00-用户态运行时.md)——上下文可能整体失效，恢复策略是"重建"而不是"修复现场"。

### 6.4 错误注入：没有它，恢复代码等于没测过

**错误注入是这一层最重要的工程实践。** 内核提供了系统化的故障注入框架，可以按概率、间隔、次数给内存分配、页分配、用户态拷贝、块设备请求等路径注入失败；对 PCIe 还有专门的 AER 注入通道（一个字符设备 + 用户态工具）。

**为什么必需**：错误恢复代码的特点是"平时不执行、一旦执行就必须正确"，而且执行路径长、涉及多个驱动协作。**不主动制造错误，这段代码基本处于未验证状态**——真出事时才发现它有问题，代价就是一次线上故障。

有一条官方给出的约束很能说明注入的严谨性：**可以被注入错误的函数必须满足两个条件**——失败时返回错误码且调用方正确检查了它，以及**在首次返回错误之前不得改变任何状态**。第二条保证了注入是"干净的失败"，不会留下半成品状态。

## 七、这一层与 L4 的边界

两者容易混淆，边界可以这样记：

| | L3 内核与系统 | L4 用户态运行时 |
|---|---|---|
| **典型动作** | 枚举、probe、映射、隔离、复位 | 提交、doorbell、事件同步、内存池 |
| **频率** | 低频（初始化、错误处理） | 高频（每次 launch） |
| **优化目标** | 正确性、隔离、可恢复 | 延迟、吞吐 |
| **出错后果** | 系统级（内核崩溃、安全边界失守） | 进程级（上下文失效） |

**一句话**：**L3 负责"设备可以被安全地用"，L4 负责"设备可以被快速地用"。** 热门路径（提交）被有意放到用户态，而冷路径（映射、隔离、复位）留在内核——这个分工正是 [overview.md](../overview.md) 里"压控制/同步税"的具体形式。
