# 框架与模型：把卡交给用户

> **这一层在讲什么。** 前面几层都在把硬件做出来、把驱动和运行时铺好；到了这一层，**用户面对的已经不是卡，而是 `import torch`**。L6 讲的就是这个界面：模型怎么跑起来、跑不快的时候卡在哪、精度是怎么被压下去的。
>
> **本文建立概念，不追求精确。** 想知道"这套软栈到底多快、怎么测"，看 [01-框架指标](01-框架指标.md)。
>
> **和上下层的关系。** 往上看，[L7](../L7-分布式与集群/00-集群是什么.md) 把这一层的工作切到多张卡上；往下看，这一层每一个算子最终都要变成 L5 的指令、L4 的提交、L2 的队列条目。**L6 是"税"最容易被白交掉的地方**——框架层的类型检查、跨设备拷贝、kernel launch 次数，都会直接吃掉下面几层辛苦省出来的性能。

---

## 一、为什么需要这一层

一块 NPU 再快，也没法直接跑一个模型。中间必须有东西负责四件事：

| 职责 | 问题 | 典型产物 |
|---|---|---|
| **表达** | 用户怎么描述模型 | PyTorch / MindSpore / JAX 的算子与自动微分 |
| **调度** | 几百个算子按什么顺序、什么时候下发 | 算子 dispatch、流与事件、图执行 |
| **优化** | 怎么把数学变成高效的指令序列 | 图编译、算子融合、kernel 生成 |
| **服务** | 怎么同时服务很多请求还不超时 | 连续批处理、KV cache 管理、调度器 |

前两件是"能跑"，后两件是"跑得快、跑得划算"。**L6 的难点几乎都在后两件**，因为它们要在"通用性"和"性能"之间做取舍——这也是为什么同一个模型换引擎能差出几倍。

---

## 二、模型这一侧：有哪些模型

选型时最先碰到的不是框架，而是"我要跑的模型长什么样"，因为它直接决定硬件需求：

| 模型结构 | 特点 | 对硬件的诉求 |
|---|---|---|
| **Dense Transformer** | 每个 token 都过全部权重 | 算力 + 显存带宽；权重必须全放显存 |
| **MoE（混合专家）** | 每个 token 只激活一部分专家 | **对互联带宽极敏感**——每 token 要做 all-to-all 路由；显存要装下全部专家 |
| **长上下文 / 多模态** | 输入极长或含图像，KV cache 巨大 | 显存容量与带宽；prefill 算力 |
| **小模型 / 端侧** | 参数少、要低延迟 | 内存带宽与量化支持 |

**同一个集群，换模型结构结论可能反转**——MoE 装不下一个高速域就会崩，dense 模型则更纯粹地吃算力与带宽。这一点在 L7 里还会再遇到。

模型的规模还有两个常被混淆的口径：**总参数量**（决定显存占用）与**激活参数量**（决定每 token 的算力开销）。MoE 正是靠这两者的分离来"用显存换算力"。

## 三、框架这一侧：模型怎么跑起来

### 3.1 为什么需要"自定义后端"

PyTorch 原生只认识 CPU / CUDA 等少数设备。国产卡或新硬件要接进来，有两条路：

| 路线 | 做法 | 代价 |
|---|---|---|
| **Fork 分支** | 直接改 PyTorch 源码加一个设备类型 | 每次上游升级都要重新合并，长期维护成本极高 |
| **自定义后端** | 用官方预留的扩展点接入，不改 PyTorch 本体 | 受扩展点能力限制，但能跟上社区版本 |

官方为这条路准备的是 **PrivateUse1**：一个预留的"私有用途"设备类型，厂商把名字、内存分配器、算子实现注册上去，用户侧就能像用 CUDA 一样用这块卡。这条路是**PyTorch 2.1 之后才真正可用**的——在那之前缺少 Storage、AMP、Distributed 等支持。

一个新后端大致要做完这些（API 名来自[官方教程](https://docs.pytorch.org/tutorials/advanced/privateuseone.html)）：

| 要做的事 | 关键接口 |
|---|---|
| 注册算子实现 | `TORCH_LIBRARY_IMPL(aten, PrivateUse1, m) { m.impl("add.Tensor", ...); }` |
| 兜底：未实现的算子回退 | `m.fallback(...)` + `at::native::cpu_fallback(op, stack)` |
| 反向传播 | `TORCH_LIBRARY_IMPL(aten, AutogradPrivateUse1, m)` |
| 自动混合精度 | `AutocastPrivateUse1` + `KERNEL_PRIVATEUSEONE` |
| 随机数生成器 | `c10::GeneratorImpl` + `REGISTER_GENERATOR_PRIVATEUSE1` |
| 设备切换保护 | `c10::impl::DeviceGuardImplInterface` + `C10_REGISTER_GUARD_IMPL` |
| 给后端改名（npu/mlu/musa…） | `torch.rename_privateuse1_backend("npu")` |
| 注册设备模块 | `torch._register_device_module("npu", torch_npu.npu)` |
| 生成 `Tensor.npu()` 这类便捷方法 | `torch.utils.generate_methods_for_privateuse1_backend(...)` |

**两条容易被忽略的约束：**

1. **一个进程里只能有一个 PrivateUse1 后端生效。** 官方教程原文说明：由于 DispatchKeySet 有 64 位硬上限、且每次集成都要改大量文件，所以 PyTorch 放弃"每个厂商申请独立 key"的方案，共享同一个 PrivateUse1。官方同时指出这些树外后端"很少被同时使用"，所以这个限制在实践中影响有限——**但你不能在同一进程里同时用两块不同厂商的卡**。
2. **改名只能做一次。** `rename_privateuse1_backend` 的官方文档明确：每个进程只能调用一次，重复设置会报错。

### 3.2 国产卡实际是怎么接的

这不是纸上方案，各家接入方式的**源码级证据**：

| 厂商 | 接入方式 | 证据 |
|---|---|---|
| 华为昇腾 | PrivateUse1 | 官方仓库 README 原文「通过 PrivateUse1 将算子和设备资源接入 PyTorch」；PyTorch 官方教程也点名昇腾作为 PrivateUse1 集成示例 |
| 寒武纪 | PrivateUse1 | `torch_mlu/__init__.py` 中调用 `rename_privateuse1_backend("mlu")`；仓库分支名为 `r1.22_pt2.1.0` |
| 摩尔线程 | PrivateUse1 | `torch_musa/__init__.py` 中调用 `rename_privateuse1_backend("musa")`，并设有 `TORCH_MIN_VERSION = Version("2.11.0")` 的版本门禁 |
| 海光 DCU | **未核实** | 未找到官方 PyTorch 适配仓库或文档；仅见第三方文章与 SGLang README 的 "Integrations in progress" 提及 |

> 几条工程上的观察：**昇腾自 2.5.1 起 `import torch_npu` 不再是强制的**（改为自动注册）；**寒武纪仓库里仍有 `pytorch_patches/` 目录**，说明除了标准接口外仍需对上游打补丁；**摩尔线程对 PyTorch 版本卡得很死**（恰好 2.11.0），版本错配会直接报错。这些都说明"接入 PyTorch"不是一次性工作，而是**要跟着上游版本持续跟的维护负担**——这正是当初选择"不改 PyTorch 本体"这条路的代价与收益。

### 3.3 算子从哪来

模型是由算子拼出来的，算子谁来写，决定了性能上限：

1. **复用现有实现**：能映射到已有算子就映射，最省事但常常不是最优。
2. **手写 kernel**：针对具体形状/精度写专用实现，性能好但数量爆炸。
3. **编译器生成**：让图编译器把算子融合、自动生成代码（见 3.4），通用性与性能的折中。

实际产品三条都会用：**热门算子手写，长尾算子靠编译器兜底**，剩下的才回落到逐元素实现。

### 3.4 图编译：把 Python 的账算回来

PyTorch 默认是**逐算子即时执行**（eager）：每个算子单独下发、单独调度。这带来两个问题——Python 解释开销大，算子之间的中间结果要反复读写显存。

图编译的思路是**先把计算图捕获下来，再整体优化**：

```
Python 模型
   ↓ 捕获（把逐算子执行记录成图）
计算图 IR
   ↓ 图优化（算子融合、常量折叠、layout 变换）
优化后的图
   ↓ 代码生成（生成 kernel，或映射到后端算子库）
硬件可执行代码
```

顺带解决一类"看起来是硬件问题"的性能问题：**kernel launch 太碎、中间结果反复落显存**。这也是它和 L5（编译器与算子）的交界处——L6 负责"捕获与表达"，L5 负责"怎么变成高效指令"。

官方这一栈的分工（来自 PyTorch 官方文档）：

| 组件 | 职责 |
|---|---|
| **TorchDynamo** | Python 层的 JIT 编译器，挂在 CPython 的帧求值接口上捕获计算图，产出 FX Graph |
| **AOTAutograd** | 提前捕获反向传播（训练场景的关键） |
| **TorchInductor** | 默认后端编译器；NVIDIA / AMD / Intel GPU 上以 OpenAI Triton 为核心构造块 |
| **FX Graph** | 前后端之间的 IR（这也是接自家后端的接口点） |

**graph break（图断裂）是这套机制里最核心的概念。** Python 代码里总有编译器不支持的写法（打印、条件分支、调用外部库），Dynamo 的处理方式是：**中断编译 → 原样跑那段不支持的代码 → 恢复编译**。后果是图被切成若干段，段之间的优化（尤其是算子融合）就做不成了。所以调优时常做的一件事就是**数图断裂、把热点区域的断裂消掉**——`fullgraph=True` 可以让第一个断裂直接报错，逼你正视它。

**给自己后端接图编译器**有两条路：注册一个后端函数（签名是 `(gm, example_inputs) -> Callable`），或通过名为 `torch_dynamo_backends` 的入口点声明。

### 3.5 顺带说说 CUDA Graph

GPU 侧还有一个和"提交开销"有关的机制值得单独提：**把一连串 kernel 录制成一个图，之后一次提交整图回放**，从而把几十上百次 launch 压成一次。官方说法是它"能消除从 Python 逐 kernel 启动的开销"，在**CPU 开销大或计算量小的模型上收益最明显**。

但它有一组硬约束，理解了这些就理解了它的适用边界：

- **不能有任意的控制流**（可用 `torch.cond` 表达的条件分支能捕获）
- **不能有 host↔device 同步**（例如 `.item()`）——这会直接报错
- **kernel 入参固定为录制时的值**，显存地址也固定（地址里的内容可以变）
- **不能有必要的 CPU 操作或 CPU 侧副作用**

这组约束解释了为什么它只适合**稳态、重复、形状固定**的推理/训练迭代——也就是恰好是 decode 阶段最想要的东西。PyTorch 侧提供了 `torch.compile(mode="reduce-overhead")` 和 `torch.cuda.graph()` 这类入口，vLLM 也把它做成了可配置项（`NONE`/`PIECEWISE`/`FULL`/`FULL_DECODE_ONLY`/`FULL_AND_PIECEWISE`）。

## 四、服务这一侧：怎么把模型变成能卖的容量

训练只要跑得完，推理要**同时满足延迟和吞吐**，这是完全不同的优化目标。五种关键技术：

| 技术 | 解决什么 | 出处 |
|---|---|---|
| **连续批处理（continuous batching）** | 不等整批做完再发下一批，请求一完成就补新的进来，让 context 阶段与 generation 阶段的序列能并行处理 | TensorRT-LLM 官方文档称为 in-flight batching / iteration-level batching |
| **PagedAttention** | 把 KV cache 分块管理，避免为每个请求预留最大长度的显存，也支持请求间共享 | 论文 [arXiv:2309.06180](https://arxiv.org/abs/2309.06180)（SOSP 2023） |
| **前缀缓存（prefix caching）** | 相同前缀（如 system prompt）只算一次，命中则跳过这段计算 | vLLM 的 Automatic Prefix Caching；SGLang 的 RadixAttention（[arXiv:2312.07104](https://arxiv.org/abs/2312.07104)） |
| **chunked prefill** | 把长输入的 prefill 切成块，与 decode 请求混批，平衡算力受限与访存受限 | vLLM V1 中**默认开启**；学术来源 SARATHI（[arXiv:2308.16369](https://arxiv.org/abs/2308.16369)） |
| **PD 分离** | prefill 与 decode 瓶颈不同，拆到不同实例上分别调 TTFT 与 ITL | vLLM 官方文档标注为实验特性 |

这些技术的共同点是：**都在把"显存"和"时间"这两种稀缺资源重新分配**。理解它们最好的角度是回到 [01-框架指标](01-框架指标.md) 里的两个延迟指标——TTFT 由 prefill 决定，TPOT 由 decode 决定。

两条值得记住的官方澄清：

- **前缀缓存只加速 prefill，不加速 decode**——它减少的是"处理查询"的时间，不是"生成 token"的时间。所以它对长文档问答、多轮对话收益大，对纯长输出的任务收益小。
- **PD 分离并不能提升吞吐**。vLLM 官方原文明确说了这一点，它的价值在于**把 TTFT 和 ITL 解耦、分别调优**，以及控制尾延迟。所以"要不要做 PD 分离"是个延迟问题，不是吞吐问题。

## 五、数值与精度：为什么可以"少算一点"

大模型对数值误差相对宽容，于是可以用更低的精度换更多的算力和带宽——这是过去几年最有效的加速手段之一。

### 5.1 常用格式的取舍

下表是**符号位-指数位-尾数位**（S-E-M）的划分，逐行来自 PyTorch 官方 dtype 文档：

| 格式 | S-E-M | 特点 |
|---|---|---|
| FP32 (`float32`) | 1-8-23 | 训练基准，但带宽开销大 |
| TF32 | 1-8-10 | 借 FP32 的范围、用 FP16 的精度做矩阵乘（NVIDIA 的中间格式） |
| FP16 (`float16`) | 1-5-10 | 精度够但**动态范围窄**，容易上溢/下溢 |
| BF16 (`bfloat16`) | 1-8-7 | 动态范围与 FP32 相同，精度低于 FP16——训练最常用 |
| FP8 (`float8_e4m3fn`) | 1-4-3 | 精度优先，适合前向与权重 |
| FP8 (`float8_e5m2`) | 1-5-2 | 范围优先，适合梯度 |
| MX 缩放因子 (`float8_e8m0fnu`) | 0-8-0 | **没有符号位、没有尾数位**——只能表示 2 的幂，专门当缩放因子用 |
| FP4 (`float4_e2m1fn_x2`) | 1-2-1 | **两个 4-bit 值打包进一个字节**，必须配合缩放因子 |

**关键洞察是"精度"和"范围"是两件事**：BF16 尾数比 FP16 少，但因为指数位和 FP32 一样，所以它能表示的范围与 FP32 相同——训练中"梯度很小或很大"的情况不会直接溢出。这就是为什么训练偏爱 BF16 而不是 FP16。

**两个容易搞错的点：**

- **FP8 不是 IEEE 标准。** E4M3/E5M2 的格式来自论文 [FP8 Formats for Deep Learning](https://arxiv.org/abs/2209.05433)（arXiv:2209.05433），规范化则由 [OCP 的 OFP8 行业规范](https://www.opencompute.org/documents/ocp-8-bit-floating-point-specification-ofp8-revision-1-1-final-pdf)承担。E4M3 有个特别之处：它**不表示无穷大**，NaN 也只有一种尾数位型，靠这个把动态范围尽量做大——这也是 PyTorch 给它起名 `e4m3fn`（"f" = finite，无无穷；"n" = NaN 编码与 IEEE 不同）的原因。
- **命名后缀有含义**：`f` = 只编码有限值、没有无穷；`n` = NaN 编码与 IEEE 规范不同；`uz` = "unsigned zero"，没有负零。看到 `float8_e4m3fnuz` 就知道它是另一种实现约定。

> 具体的十进制极值（例如某格式最大能表示多少）本文不列：这些数字必须从 OCP 规范 PDF 正文逐条核对，凭记忆写很容易出错，而位宽划分本身已经足够说明问题。

### 5.2 量化：精度不够，用缩放补

低精度格式的范围太窄，直接塞进去会溢出。解决办法是**分块 + 缩放因子**：把张量切成小组，每组单独算一个缩放系数（scale），存储时只存低位值、用的时候再乘回来。MX（Microscaling）格式把这套做法标准化了，它由三个要素组成：**元素格式**（如 FP4/FP8）、**缩放因子格式**（E8M0）、**块大小**（MX 规范里是 32 个元素共用一个缩放因子）。

常见做法按粒度分几档：**按张量**（整个张量一个 scale，最简单但最粗）、**按通道**、**按块**（如 1×128 或 128×128 的块，块内共用 scale）。粒度越细、精度保持越好，代价是元数据开销变大、硬件实现更复杂。

量化有两个必须小心的后果：
- **精度损失会在长链条上累积**，尤其是推理的 KV cache 与注意力；
- **不是所有算子都能低精度**，归一化、softmax 这类对范围敏感的算子往往要保留高精度。

一个值得记住的结论（来自 AWQ 论文 [arXiv:2306.00978](https://arxiv.org/abs/2306.00978)）：**大模型里并非所有权重同等重要，只保护约 1% 的"显著权重"就能大幅降低量化误差**；而判断哪些权重显著，要看**激活分布**而不是权重本身。这解释了为什么好的量化方案不是"把所有权重一起压"，而是"挑着压"。

### 5.3 确定性

同一份代码跑两次结果不一致，会让调参和复现变成噩梦。低精度、并行归约顺序、非确定性 kernel 都会破坏确定性。**训练侧通常可以容忍，但调试与对账时必须有确定性开关**。
