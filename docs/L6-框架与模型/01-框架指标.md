# 框架指标：延迟、吞吐与效率

> **这一层在讲什么。** [00-框架与模型](00-框架与模型.md) 讲清楚了模型怎么跑起来（框架接入、图编译、推理服务、数值精度），这篇回答**怎么判断它跑得好不好**。
>
> **读法。** 只想知道"概念"，读完 00 就够；要调优、要对比引擎、要判断一份性能报告可不可信，再往下读这篇。
>
> **和 L7 的分工。** 这一层看的是**单机、单模型**的表现：这套框架把卡用到了几成、一次推理快不快。至于"加卡之后还能不能线性扩、一个集群值多少钱"，那是 [L7 集群评测](../L7-分布式与集群/01-集群评测.md) 的事。两者用同一套延迟指标（TTFT / TPOT），但**口径不同**：L6 测单请求与单实例，L7 测集群在某个交互档位下的容量。

---

## 一、为什么这一层的评测容易失真

同一张卡、同一个模型，换一个引擎或一个版本就能差出几倍。原因在于 L6 的性能由**四层效率相乘**决定，任何一层塌掉，端到端都难看：

```
端到端吞吐 = 硬件峰值 × 算子效率 × 运行时效率 × 模型结构适配度
              (L1)       (L5 算子)    (L4 提交路径)   (L6 自己)
```

这解释了一个常见困惑：**"卡跑分很高，但我的模型就是慢"**——通常不是硬件被虚标，而是后面三层里有一层没对齐（例如算子回落到慢路径、kernel launch 太碎、显存装不下导致反复换入换出）。

所以读 L6 的数字，第一件事是问：**这是哪个环节的效率？**

## 二、用户视角：延迟与吞吐

用户能感知的只有三件事，和 L7 用的是同一组定义：

| 指标 | 含义 | 由谁决定 |
|---|---|---|
| **TTFT**（首 token 延迟） | 从发出请求到看见第一个 token | prefill 阶段：算力 + 排队 |
| **TPOT / ITL**（token 间延迟） | 相邻两个 token 的间隔 | decode 阶段：显存带宽 |
| **端到端延迟** | TTFT + 输出长度 × TPOT | 两者的组合 |

三个使用要点：

1. **必须分开报。** 一句"平均延迟 500 ms"同时掩盖了这两个问题——是排队太久，还是出字太慢？优化手段完全不同。
2. **必须用分位数。** 平均值掩盖尾部，而尾部才决定体验（原因见 L7 的 [2.2 节](../L7-分布式与集群/01-集群评测.md)）。
3. **必须带 SLO 报吞吐。** 无约束的最大吞吐（例如把 batch 开到极大）没有商业意义；**满足延迟约束下的吞吐才是可卖容量**。

### 吞吐的两种口径

| 口径 | 定义 | 用来看什么 |
|---|---|---|
| **tokens/s** | 每秒生成的 token 数 | 生成侧产能 |
| **requests/s** | 每秒完成的请求数 | 服务侧产能（与输出长度耦合） |
| **samples/s** | 每秒处理的样本数（视觉类） | 非 LLM 负载 |

对 LLM 要特别注意：**tokens/s 与输出长度强相关**。报告吞吐时必须同时给输入长度、输出长度和并发数，否则数字不可比。

## 三、框架视角：这一层独有的四个指标

前面两个指标用户能感知，下面四个只有做框架/编译的人才会盯——但它们**决定了前两个指标的天花板**。

### 3.1 算子支持情况（没有"算子覆盖率"这个官方指标）

**先说一个常见的误用：业界并没有"算子覆盖率"的权威定义。** 更接近官方口径的说法是 **「最小必需算子集 + CPU fallback + 逐步补齐」**——PyTorch 官方在《Accelerator Integration》里给出的方法论原文是：

> PyTorch 内置算子超过 3500 个……目标应该聚焦在**必需算子**上，其余算子先用社区的 fallback 机制保证功能可用，之后再逐步补齐以提升性能。

新后端**必须**实现的最小算子集（官方列出，可直接对照自查）：

```
empty.memory_format        empty_strided          as_strided
view                       _reshape_alias         resize_
_copy_from                 _copy_from_and_resize  _local_scalar_dense
set_.source_Tensor         set_.source_Storage    set_.source_Storage_storage_offset
fallback（兜底路径）
```

所以实务上应该这样报告，而不是给一个百分比：

- **必需算子是否齐全**（缺了会直接报错，不是慢）
- **fallback 清单与代价**：哪些算子走了 CPU 回退、占了多少时间
- **热点算子的实现等级**：是手写 kernel、编译器生成，还是逐元素回落

**为什么这比覆盖率重要**：模型里往往是少数几个算子（注意力、归一化、MoE 路由）占了大头时间。**一个热点算子回落就能拖垮整层**，而此时"覆盖率 95%"这个数字毫无帮助——它不告诉你是哪 5% 在拖后腿。

### 3.2 图编译时间与冷启动

图编译能提升稳态性能，但代价是**编译本身要花时间**。于是有两个必须区分的数字：

- **稳态性能**：编译之后的持续吞吐（用来看上限）
- **冷启动延迟**：第一次请求要等多久（包括编译 + 权重加载）

**服务场景里冷启动是真金白银**：扩容、故障重启、版本更新时，用户等的是冷启动，不是稳态吞吐。官方文档给的量级是：**常见模型的冷启动编译时间从数秒到数分钟，非常大的模型可以到几十分钟甚至几小时**。

PyTorch 官方提供的测量手段（可直接用）：

| 手段 | 看什么 |
|---|---|
| `torch._dynamo.utils.compile_times()` | 各编译阶段分别耗时 |
| `TORCH_COMPILE_DEBUG=1` | Inductor 各阶段时间与产物 |
| `torch._logging.set_logs(recompiles=True)` | **重编译**——往往比首次编译更值得查 |
| `tlparse` / `TORCH_TRACE` | 单次编译的完整报告 |

缓解手段：**编译缓存**（编译产物可跨进程持久化）、**区域编译**（只编译重复出现的 transformer block）、以及把动态形状标注出来（`torch._dynamo.mark_dynamic`）以减少重编译。

**重编译是常被忽略的隐形成本**：Dynamo 用一组 guard（检查 dtype、device、shape、stride 等）判断能否复用已编译的图，**任何一个 guard 失败就要重新编译**。所以"输入形状忽长忽短"的服务场景，实际编译时间可能是首次编译的很多倍。

### 3.3 显存与 KV cache 占用

| 指标 | 含义 |
|---|---|
| 权重占用 | 模型参数本身（由精度决定，FP8 约为 BF16 的一半） |
| **KV cache 占用** | 随**并发数 × 上下文长度**线性增长，长上下文下往往是主要开销 |
| 激活与临时缓冲 | 中间结果；融合算子能显著降低 |
| 可支撑并发 | 上面三者之外还剩多少显存 |

**KV cache 是推理容量的真正约束**：它决定了"这台机器能同时服务多少个用户"。这也是为什么前面提到的分页管理、前缀缓存、KV 量化这些技术如此重要——它们改的不是速度，是**能装下多少并发**。

### 3.4 数值一致性

低精度的收益（更快、更省显存）必须用**精度损失**来换，所以要能度量这个损失：

- **逐层对比**：与高精度基线比每个算子的最大/平均相对误差——定位是哪一层先崩。
- **任务级指标**：困惑度、或具体任务的准确率（更贴近实际影响）。
- **确定性**：同样输入跑两次是否逐位一致。调参、对账、复现实验都依赖它。

一个实务经验：**精度问题往往不在平均值上，而在尾部**——大部分 token 都对，少数关键 token 错了，任务指标就掉了。所以要看分布，不只看均值。

## 四、效率视角：把"卡用到了几成"拆开

L6 的优化目标是把下面这个乘积推向 1：

```
实际吞吐 = 硬件峰值 × MFU（算子与访存的效率）× 运行时效率 × 并发利用率
```

| 指标 | 定义 | 低了的典型原因 |
|---|---|---|
| **MFU**（Model FLOPs Utilization） | 实际算力 / 硬件峰值 | tiling 差、算子没融合、访存受限 |
| **MBU**（Model Bandwidth Utilization） | 实际带宽 / 峰值带宽 | decode 阶段更该看这个 |
| **运行时开销占比** | 调度/提交/同步占用时间的比例 | kernel 太碎、Python 开销、同步等待多 |
| **并发利用率** | 实际并发 / 显存能支撑的并发 | 调度策略差、cache 命中率低 |

诊断顺序很重要：**先判断瓶颈类别，再谈优化**。

- **算力受限**（MFU 低但带宽没满）→ 优化 tiling、算子融合、提高并行度
- **访存受限**（带宽接近峰值）→ 提高 batch、量化权重、减少数据搬运
- **控制受限**（两者都不满）→ kernel 太碎、launch 太多，考虑图编译 / 大 kernel 融合
- **容量受限**（显存不够）→ 量化、KV cache 优化、更小并行切分

这个分类和 L1 的 Roofline 是同一套语言（见 [overview.md](../overview.md) 的层间关系表）。

## 五、怎么评测才算可信

和 L7 同一套纪律，但控制变量更严：

**必须固定的**：模型与权重版本、精度、输入/输出长度分布、并发或到达率、引擎与版本、采样参数（temperature、是否投机解码）。

**必须报告的**：TTFT 与 TPOT 分开且给分位数、吞吐、**达标口径**、以及在哪个精度下取得。

**这一层特有的坑**：

- **拿 Offline 吞吐对比 Server 延迟**——量纲不同（详见 [L7 6.1 节](../L7-分布式与集群/01-集群评测.md)）。
- **忽略编译与预热**：不区分冷启动和稳态，数字会被编译时间污染。
- **忽略前缀缓存命中率**：命中率高会让成绩显著变好，必须声明缓存的到底是哪些请求。
- **用平均精度掩盖尾部错误**：量化损失要看分布与任务指标。
- **把引擎能力当成硬件能力**：同一张卡换引擎可能差两倍，结论要写清测的是哪一层。

## 六、一张表：该看哪个指标

| 你要回答的问题 | 该看的指标 |
|---|---|
| 用户等得久不久 | TTFT p99 |
| 出字顺不顺 | TPOT p99 及其抖动 |
| 这套框架把卡用到了几成 | MFU（训练/prefill）、MBU（decode） |
| 我的模型为什么慢 | 算子支持情况（最小算子集是否齐全 + fallback 清单）+ 瓶颈类别 |
| 能同时服务多少用户 | KV cache 占用 → 可支撑并发 |
| 扩容/重启要等多久 | 冷启动延迟（含编译与权重加载） |
| 便宜不便宜 | 满足 SLO 的吞吐 ÷ 成本（跨层口径见 L7） |
| 结果可信吗 | 跑两次是否一致 + 是否用分位数 + 精度口径 |
