# 运行时指标：提交延迟、队列与拷贝

> **这一层在讲什么。** [00-用户态运行时](00-用户态运行时.md) 讲清楚了这一层的对象模型（上下文/流/事件）与快慢路径的分界；这篇回答**怎么量它、怎么判断它是不是瓶颈**。
>
> **读法。** 只想知道"概念"，读完 00 就够；要做性能优化、或者怀疑"卡没跑满其实是运行时的问题"，再往下读这篇。
>
> **这一层的指标特点**：它们通常不是"越大越好/越小越好"的单一指标，而是**成对出现的**——提交延迟要配吞吐看，拷贝带宽要配重叠率看。原因见下。

---

## 一、为什么这一层的指标必须成对看

这一层衡量的是**开销**，而开销只有在"相对于工作量"时才有意义：

- 一次提交花 5 µs 是好是坏？**取决于这次提交背后的计算要跑 3 µs 还是 3 ms**。前者开销主导（此时该做的是合并提交），后者完全可忽略。
- 一次拷贝花 1 ms 是好是坏？**取决于它能不能被计算重叠掉**。能藏住的拷贝等于免费，藏不住的拷贝是纯损失。

所以这一层所有指标都要配一个分母：**每次提交背后的工作量**、或者**可重叠的计算量**。孤立地报"提交延迟 5 µs"没有决策价值。

---

## 二、提交路径：延迟与吞吐

| 指标 | 定义 | 怎么看 |
|---|---|---|
| **单次提交开销** | 从 API 调用到命令进入队列的时间 | 要和工作量比；小任务时是主要成本 |
| **提交吞吐** | 每秒能提交多少次 | 上限由这一层和 L3 共同决定 |
| **队列深度** | 队列里能缓冲多少未完成工作 | 太浅会让设备空转 |
| **设备空转率** | 设备无事可做的时间占比 | 最直接的"喂不饱"证据 |

### 怎么测单次提交开销

关键手法是**把固定开销从总时间里摊出来**：

```
方法 A（推荐）：批量提交求平均
   提交 N 个互相无依赖的任务，测主机侧总耗时 T
   单次开销 ≈ (T − 计算时间×N) / N        （N 越大越准）

方法 B：分离主机侧与设备侧
   主机侧计时：反映"CPU 把命令送出去"要多久
   设备侧计时（用事件打点）：反映"设备真正执行"要多久
   两者之差就是提交路径的开销与排队时间
```

**为什么必须分离主机侧与设备侧**：因为 API 是**异步返回**的。主机侧测出来的时间只代表"CPU 把活发出去了"，不代表活干完了。**把主机侧时间当成设备时间，是最常见的一类误判**。

### 队列要开多深：Little's law

这一层能用上一条漂亮的关系式（对应 [overview.md](../overview.md) 的 Little's law）：

```
在制品（并发任务数）= 吞吐（任务/s）× 延迟（s/任务）
```

它的用法是**反推**：

```
要让设备不断粮，队列里至少要缓冲：
  队列深度 ≥ 设备吞吐 × 单次任务延迟
```

举例说明量级感觉：如果设备每秒能完成 10 万个任务，而每个任务从提交到完成要 20 µs，那么要保持饱和，在制品的任务数至少要 `100000 × 0.00002 = 2`——听着不多，但**如果你的提交速率只有每秒 5 万次，设备就只能跑到一半**。这就是"提交路径拖累设备利用率"的定量形式。

**推论**：当设备吞吐很高而单次任务很小的时候，运行时与驱动的提交速率会直接成为瓶颈，此时唯一有效的方向是**减少提交次数**（合并、批处理、图执行）。

## 三、内存：分配、映射与迁移

内存侧的指标可以分成三类，混淆它们会导致优化方向完全错：

| 类别 | 指标 | 典型量级感受 |
|---|---|---|
| **分配** | 单次分配延迟、池命中率 | 首次分配慢（要进内核），池内分配快 |
| **映射** | 建立映射的延迟（把设备内存映射进进程地址空间） | 通常在初始化时一次性完成 |
| **迁移** | 按需迁移的缺页次数与迁移字节数 | **隐式发生，最容易失控** |

**"分配慢"和"映射慢"是两件事**：分配是从设备/驱动要一块内存（**可能造成全局同步**、可能触发回收），映射是把它接进进程的地址空间（一次性的页表操作）。热路径上应该做的是**复用**——即"内存池"，让稳态下不出现新的分配。

> **一个容易被漏掉的量化点**：传统分配方式的一个隐藏成本不是"慢"，而是**它会打断其它所有流**——官方描述是传统分配/释放会让设备**在所有正在执行的流上同步**。也就是说，热路径上一次分配的影响会**放大到当前所有在跑的工作**上。所以**要测的不只是"分配花了多久"，还有"它让别的流停了多久"**——这也是流有序分配方式存在的理由。

**按需迁移要特别警惕**：它是隐式的，所以问题往往表现为"什么都没干却变慢了"。诊断方法是看有没有**反复迁移**——同一份数据在主机与设备之间来回搬。一旦出现，性能会塌到"带宽 × 迁移量"这一水平，和计算能力无关。

**一个定量判断**：如果迁移字节数远大于实际参与计算的字节数，说明复用率出了问题。理想情况下，每个字节应该只搬一次。

## 四、拷贝：带宽要配重叠率

| 指标 | 说明 |
|---|---|
| **H2D 带宽**（主机→设备） | 走 PCIe/CXL，受链路带宽与协议开销限制 |
| **D2H 带宽**（设备→主机） | 同上，通常与 H2D 不对称 |
| **D2D 带宽**（设备内） | 受显存带宽限制，通常远高于跨链路 |
| **P2P 带宽**（设备→设备） | 取决于有没有直连（NVLink/RoCE），没有就得绕主机 |
| **重叠率** | 拷贝被计算藏住的比例——**最该看的那个数** |

**要区分四种拷贝路径**，它们的量级差很多，混在一起报"拷贝带宽"没有意义。

**重叠率为什么最重要**：拷贝本身往往不可避免（数据总要从主机来），但**是否占用关键路径**是可以优化的。用多条流把拷贝与计算错开，就能把拷贝时间藏进计算时间。判断方法很直接：

```
串行执行：总时间 = 拷贝时间 + 计算时间
重叠之后：总时间 ≈ max(拷贝时间, 计算时间)
```

如果实测总时间接近两者之和，说明**没有重叠**——这通常不是硬件问题，而是**没有分多条流**（回到 [00](00-用户态运行时.md) 里那条"流内有序、流间无序"的规则）。

## 五、同步：精度与代价

事件既用来计时也用来同步，这两种用途的指标不同：

| 指标 | 用途 | 注意 |
|---|---|---|
| **事件计时精度** | 测量设备侧耗时 | 打点本身有开销，密集打点会扰动被测对象 |
| **同步等待时间** | 跨流依赖、等待结果 | 过长的同步等待说明并行度不足或依赖设计不好 |
| **隐式同步次数** | 由默认流等机制引起的意外串行 | **看不见的同步最贵** |

**"隐式同步"是这一层最隐蔽的性能杀手**：它不体现在任何显式的同步调用里，却把本该并行的流串起来。典型来源是默认流的特殊语义。诊断方式很朴素——**看时间线**：如果流上出现了本不该有的空隙，找是谁在等谁。

## 六、怎么评测才算可信

**必须固定的**：设备型号与频率状态（锁频）、驱动与运行时版本、队列深度与流数量、内存是否预热（池是否已建立）、是否启用了 profiling 本身。

**必须报告的**：主机侧时间与设备侧时间**分开**、拷贝的四种路径分别给、以及**重叠率**。

**这一层特有的坑**：

- **把异步返回当成完成**：主机侧计时只代表命令发出去了。
- **忽略首次开销**：首次分配、首次建立映射、首次编译都比稳态慢得多，混进平均值会失真。
- **profiling 改变被测对象**：计数器采集、时间线追踪、频繁打点都会带来可观测性开销，必须给出"开/关 profiling 的对比"。
- **用单流测并行场景**：默认流或单流会把并行度压成 1，测出来的不是设备能力。
- **把隐式迁移当成"正常开销"**：迁移抖动是可以消除的（显式管理数据位置），不该被接受为常态。
- **忽略 host 侧 CPU 成本**：设备很快时，CPU 提交与同步会主导端到端，此时优化对象是主机代码而不是设备。

---

## 七、一张表：该看哪个指标

| 你要回答的问题 | 该看的指标 |
|---|---|
| 提交路径是不是瓶颈 | 单次提交开销 ÷ 单次任务计算时间 |
| 设备为什么没跑满 | 设备空转率 + 队列深度是否足够（Little's law 反推） |
| 拷贝拖慢了多少 | 四种拷贝路径带宽 + 重叠率（能不能被藏住） |
| 有没有内存抖动 | 迁移字节数 vs 参与计算的字节数 |
| 稳态会不会频繁分配 | 内存池命中率、稳态下的分配次数 |
| 是不是被隐式串行拖累 | 时间线上的空隙 + 隐式同步次数（默认流语义） |
| 结果可信吗 | 主机/设备时间是否分开 + profiling 是否改变了测量 |
