# 用户态运行时：把设备变成程序能用的资源

> **这一层在讲什么。** 内核和驱动（L3）已经把设备接进了系统，但应用程序没法直接用系统调用去操作它——太底层、太慢、太容易出错。中间需要一层**用户态运行时**，把设备包装成程序好用的对象：**上下文、流、事件、内存、队列**。这一层讲的就是这套对象模型，以及它为什么长这样。
>
> **本文建立概念，不追求精确。** 想知道"一次提交要多少微秒、队列要开多深"，看 [01-运行时指标](01-运行时指标.md)。
>
> **和上下层的关系。** 上面看，[L5](../L5-编译器与算子/00-编译器与算子.md) 生成的指令流要靠这一层提交；下面看，这一层每个动作最终都要变成 L3 的驱动调用甚至系统调用。**这一层是"控制/同步税"的主战场**——一次 launch、一次 doorbell、一次加锁往返，都要在这里被压到最低。

---

## 一、为什么不能直接操作设备

最朴素的想象是：应用程序把命令写进设备寄存器，设备算完发中断。这条路径能通，但没人这么用，原因有三个：

| 问题 | 后果 |
|---|---|
| **每个动作都要进内核** | 系统调用开销是百纳秒到微秒级，而一次 kernel 可能只跑几微秒 |
| **没有隔离** | 多个进程共享同一张卡，需要地址空间和资源的隔离 |
| **硬件接口太脏** | 队列格式、寄存器偏移、中断号都是硬件细节，不能暴露给业务代码 |

于是用户态运行时的核心设计目标就是：**把危险的操作收进内核（慢但安全），把高频操作留在用户态（快但受控）**。这条分界线画在哪里，决定了一整套 API 的形态。

## 二、对象模型：上下文、流、事件

四个对象撑起了整个用户态接口：

| 对象 | 是什么 | 解决什么 |
|---|---|---|
| **设备（device）** | 一张卡或一个虚拟设备 | 资源枚举与选择 |
| **上下文（context）** | 一个地址空间 + 一堆资源的容器 | **隔离**：进程之间互不干扰；也是"上下文丢失"这种错误的作用域 |
| **流（stream）** | 一条有序的命令队列 | **并发**：流内严格有序，流间可以并行 |
| **事件（event）** | 一个可等待的标记点 | **同步**：跨流依赖、计时 |

### 一条最重要的规则：流内有序，流间无序

这条规则解释了这个模型几乎所有的行为：

- 同一条流上的命令**按提交顺序执行**，你不需要为它们加同步——官方把它叫做"**in-order stream**"，一个操作**不能越过**同流中的其它操作；
- 不同流上的命令**没有顺序保证**，要建立依赖必须显式同步（用事件等）；
- 因此"能不能并行"取决于你**有没有把工作拆到多条流上**——设备空闲往往不是硬件不够，而是软件没给它并行度。

> **一处必须标注版本的引用**：官方关于"流间无序"的经典表述是——*不同流之间，命令**可能**乱序或并发执行；这种行为**不被保证**，因此不应依赖它来保证正确性（例如流间通信是未定义的）*。但这句话**只出现在 CUDA 12.6.3 及更早的编程指南里**，现行版本文档只保留了"流内有序"的表述。**引用流间无序时请注明版本**——否则会被认为是现行文档的原文。

**流的真正用途是划分并行阶段**：把互相独立的计算放到不同流，把拷贝和计算重叠起来，把不同请求隔离开。这也是为什么运行时的性能优化常常归结为一句"你有没有正确地分多个流"。

### 事件的两个用途

事件（event）这个概念经常被混用，其实它承担两件事：

1. **同步**：让一条流等待另一条流上的某个点完成（跨流依赖的建立方式）。官方语义是"让**之后**提交到该流的所有工作都等待这个事件所捕获的全部工作"——注意**它对已经提交的工作无效**，只管之后。
2. **计时**：在流上打点，测量这一段命令真正在设备上花了多久——比主机侧计时准确得多，因为主机侧的调用是异步返回的。官方给出的分辨率量级是**亚微秒级**。

> 计时有一个实操陷阱：**如果创建事件时禁用了计时功能，再去取时间差会直接返回错误**。所以"用来同步的事件"和"用来计时的事件"要按用途创建。

**同步与计时还有两种等待方式**：阻塞等待（不占 CPU）与忙等（延迟更低但占一个核）。**这是"用 CPU 换延迟"的又一次出现**——和后面要讲的轮询完成是同一个取舍。

### 一个必须知道的坑：默认流的隐式同步

多数运行时都提供一个"默认流"，而**默认流往往有特殊的隐式同步语义**——它会和其它（非默认）流产生同步关系。结果是：你以为自己在并行，实际上被默认流串起来了。

官方把这件事描述得很具体（以 CUDA 的 legacy default stream 为例）：

> legacy 默认流是一个**隐式流**，它会与同一个上下文里的**所有其它流同步**（非阻塞流除外）。顺序是：legacy 流**先等**所有阻塞流，然后这个操作在 legacy 流中排队，接着**所有阻塞流再等** legacy 流。

也就是说**一次 legacy 流上的操作，会把它前后的所有阻塞流都串起来**——这就是隐式串行的来源。

**两代默认流要分清**（这是接入新卡时最容易忽略的细节）：

| 默认流 | 同步行为 |
|---|---|
| **legacy 默认流** | 与同上下文内所有**阻塞流**双向同步（上面那段原文） |
| **per-thread 默认流** | **只属于该线程与上下文**，不与其他流同步；但它**会与 legacy 默认流同步**（如果两者都被用到） |

**非阻塞流**是另一个关键概念：创建流时声明为非阻塞，**就能避开 legacy 默认流的隐式同步**。

所以工程上有三条常见做法：**显式创建自己的流**、把流声明为**非阻塞**、或改用 **per-thread 默认流**模式。**这条细节是新卡接入时最容易被忽略、又最容易白丢性能的地方。**

## 三、命令提交：这一层的核心快路径

一次提交从 API 调用到硬件执行，大致经过：

```
应用调用（如 launch kernel）
    ↓  运行时：参数校验、组装成硬件认识的命令格式
    ↓  写入命令队列（通常在用户态内存里，无需进内核）
    ↓  通知设备"有新命令"（写寄存器 / doorbell）
    ↓  设备读取并执行
```

**关键设计是"队列在用户态内存里"**：应用程序把命令写进一块双方共享的内存，然后只用一个写寄存器（或类似的轻量通知）告诉设备去看。**这样就避免了每次提交都进内核。**

由此产生了这一层最重要的几个工程概念：

- **提交开销（per-launch cost）**：即使队列在用户态，一次提交仍有固定开销（校验、组装、原子操作）。当单个计算任务很小（例如一个逐元素算子）时，**开销可能超过计算本身**。
- **批处理与合并**：把多个小任务合成一次提交，摊薄固定开销。图执行（把整张图录制下来一次提交）就是这条思路的极致形式。
- **队列深度**：队列能排多深，决定了设备"断粮"前能缓冲多少工作。队列太浅会频繁空转。
- **doorbell 覆盖量**：一次通知能让设备取走多少工作。这是硬件/固件设计决定的，运行时只能尽量把工作攒够再敲。

> **术语说明**：**"doorbell"（门铃）在 Linux 内核驱动源码里有明确定义**，不是纯口头说法。AMD 的 KFD 驱动把它描述为"一个 PCI MMIO 区域，接收 32 位写入并作为队列的写指针传递"，并明确**它就是给用户态应用写队列用的**；Intel 的 Xe 驱动文档也把它定义为"让用户态应用**无需每次提交都陷入内核**就能向硬件提交工作的机制"。
>
> 这个定义比"写寄存器通知设备"更准确：**doorbell 传递的是队列的写指针，不是命令内容本身**——这也正是它轻量的原因。不过要注意 **CUDA 官方文档并不使用这个词**，而有的运行时（如 Level Zero）改用 Command Queue / Command List 这套概念。所以不同厂商文档用不同术语描述同一件事是正常的，按语义理解即可。

## 四、内存管理：这一层最复杂的一块

设备内存不是"分配一块内存"那么简单，它要同时满足：设备能直接访问、主机能访问、多个设备能共享、地址要能映射到进程空间。于是有了四个层次的机制：

| 机制 | 解决什么 |
|---|---|
| **分配器 / 内存池** | 避免频繁申请释放带来的开销与碎片 |
| **统一虚拟地址（UVA）** | 主机与设备用**同一套虚拟地址空间**，指针到哪都能用 |
| **统一内存 / 按需迁移** | 数据可以"先放主机"，用到时自动迁到设备 |
| **固定（pin）与映射** | 让设备能直接访问主机内存（前提是页不能被换出去） |

**要区分两个容易混淆的概念**：统一虚拟地址解决的是"**指针通用性**"（同一块内存在主机和设备上地址一致），统一内存解决的是"**数据自动搬家**"（页面在两边之间迁移）。前者是地址空间设计，后者依赖缺页机制和迁移策略——**别把两者当成同一件事**。

**按需迁移的收益与风险**同样重要：

- 收益：编程简单，不用手动管理数据在哪；数据量超过设备显存时也能跑。
- 风险：**迁移是隐式发生的**，一旦访问模式不好（例如反复来回访问同一份数据），会出现"抖动"——大量时间花在搬运而非计算上，而且主机侧很难看出原因。

所以高性能代码倾向于**显式控制数据位置**（手动拷贝、预取），把迁移显式化、可预测化。

**这里有一个很少被讲清楚但很关键的事实**：**分配本身可能造成全局同步**。官方对传统分配方式的描述是——用 `cudaMalloc` / `cudaFree` 管理内存会**让设备在所有正在执行的流上同步**。这正是后来引入"**流有序内存分配**"的动机：把分配与释放**按流排序**，让它们与流上的其它工作一样排队，而不是打断所有流。

**两者的定位差异可以这样记**：

| 方式 | 特点 |
|---|---|
| **传统分配（`malloc`/`free` 式）** | 简单直观；但**会造成全局同步**，且频繁分配释放开销大 |
| **流有序分配 + 内存池** | 分配释放按流排序、不打断其它流；配合内存池复用，适合热路径 |

**内存池还提供了几个可调项**，理解它们就理解了池的取舍：**释放阈值**（保留多少已申请内存不还给系统——太小会频繁向系统申请，太大则占着内存不放），以及三个**复用策略开关**（是否允许按事件依赖复用、是否允许机会性复用、是否允许内部依赖复用）。**这些开关决定了"池会不会把内存还给系统、以及多快能复用到同一块内存"**。

> **一个实务后果**：因为传统分配会全局同步，所以**在热路径上反复分配释放是灾难**——这既是内存池存在的理由，也是"预分配 + 自己管"这个常见做法的依据。

## 五、跨进程与跨设备共享

当数据要在"两个进程"或"两张设备"之间流转时，不能简单传指针（各自的地址空间不同）。标准做法是**让内核持有一个共享对象的句柄**，各方通过句柄映射到自己的地址空间：

```
进程 A 分配内存 → 内核导出为一个"可共享对象"（句柄）
                          ↓ 传递句柄（socket / 文件描述符等）
进程 B 用句柄映射 → 得到自己地址空间里的指针
                          ↓ 双方约定同步
两个进程直接读写同一块物理内存（无需拷贝）
```

Linux 上承担这个角色的机制是 **dma-buf**：它定义一个**跨设备、跨驱动共享缓冲区的通用框架**，让"分配方"（exporter）和"使用方"（importer）可以是不同的驱动或设备。显示子系统与图形栈之间的共享（PRIME）就是它的典型应用——用户态看到的 PRIME 缓冲区**就是一个 dma-buf 的文件描述符**。

它由三个原语组成，这个划分很能说明问题：

| 原语 | 作用 |
|---|---|
| **dma-buf** | 缓冲区本身，以文件描述符暴露，可跨进程/子系统/设备传递 |
| **dma-fence** | **异步硬件操作的完成信号** |
| **dma-resv** | 管理某个缓冲区上的一组 fence，负责隐式同步 |

**注意第二、三个原语的存在本身就说明了一件事**：共享缓冲区不是"给个 fd 就完事"——**你必须能表达"这块数据现在能不能被安全访问"**。因为设备是异步的，"我拿到指针了"不等于"数据已经就绪"。**这正是 L2 里"完成语义与内存序"在运行时层的延续。**

> **一个必须纠正的常见误解**：**dma-buf 是共享框架，不等于"保证零拷贝"。** 两个限定条件：
>
> 1. **CPU 访问共享缓冲区必须用同步 ioctl 包住**（开始访问/结束访问这一对）。官方明确说：**用户态不能假定访问是一致的**——即使某些系统上"不调用也能工作"。这直接关系到数据可见性。
> 2. **导出方在挂载之前仍然可以迁移底层存储**，迁移时通过失效通知让使用方销毁并重建映射。**所以"共享"并不冻结数据位置。**

**为什么这一层仍然很关键**：它是 **零拷贝的前提**。没有这套机制，跨进程传数据只能靠"拷贝到中转缓冲区"，而大模型场景下动辄几百 MB 的张量，拷贝就是纯浪费。这也对应 [overview.md](../overview.md) 里"抽象税"那一类——**快路径存在的意义就是让这类税不出现在热路径上**。

**用共享内存句柄做进程间通信还有一堆实际限制**（以 CUDA 的 IPC 为例，官方逐条列出）：**只支持 Linux**；**不支持统一内存分配**；要求父子进程用**相同的驱动与运行时版本**；而且因为分配器会做子分配，**共享句柄可能把底层大块内存里的其它子分配一并共享出去，造成进程间信息泄露**——官方因此建议**只共享 2 MiB 对齐的分配**。**这一条很值得记住：共享粒度不由你决定，而由分配器决定。**

## 六、可观测性：没有计数器就没法优化

运行时提供的第二类能力是"让程序看见设备在干什么"：

| 能力 | 回答什么问题 |
|---|---|
| **时间线追踪（timeline tracing）** | 各条流上的任务怎么排布、哪里有空隙、拷贝与计算有没有重叠 |
| **性能计数器（hardware counters）** | 算力/带宽利用率、缓存命中等硬件级事实 |
| **调用追踪与 API 拦截** | 主机侧到底发了什么、每次调用的开销 |

**为什么时间线是第一步**：它不需要理解硬件就能看出最粗的问题——**串行化、气泡、没有重叠**。很多"性能问题"在这一步就能定位，不用去看计数器。

**这两类工具测出来的"同一个 kernel 的耗时"可以不一样**，官方对此有明确说明：**时间线工具与计数器工具测量 workload 时长的方式不同，因此同一 workload 在两个工具里报告的时长会有差异**。原因是计数器工具通常会**锁定频率**（否则计数器与频率相关的指标没有意义），并插入额外的等待与打点。

**这条事实很实用**：**两个工具的数字不一致不是 bug，而是方法不同**；更要紧的是，**在计数器工具下"无法用主机侧计时或事件计时得出该 workload 的真实时长"**——因为测量方法已经改变了时序。所以**报告性能数据时必须说明测量工具与是否锁频**。

**计数器的价值**在于区分"看起来慢"和"实际上受限"：时间线告诉你某个 kernel 花了 200 µs，计数器才告诉你是算力打满了、还是访存受限、还是指令发射不足。这和 [L5 的瓶颈分类](../L5-编译器与算子/01-编译与算子指标.md) 是同一套语言，只是观测点更靠下。

## 七、错误模型：异步带来的固有难题

因为提交是异步的，**错误也会异步出现**——调用返回时可能什么都没发生，错误在几个 API 调用之后才浮出来。官方文档把原因说得很清楚：

> 流中的错误可能来自流里的**任何**操作（包括 kernel 启动与内存传输），但这些错误**在流被同步之前可能不会回传给用户**——例如等到等待事件、或调用流同步时。

这带来两个后果：

1. **错误归属困难**：报错的位置不是出错的位置。所以调试时要靠同步点切分区间，逐步缩小范围；也可以用环境变量把所有启动改成同步执行，牺牲性能换取错误位置的准确性。
2. **有些错误不可恢复**：设备侧的严重错误会让**整个设备状态失效**。

### 官方怎么描述"不可恢复"

**先澄清一个常被误用的术语**："sticky error（黏性错误）"**不是官方术语**——在 CUDA 官方文档中检索不到这个词，它是社区与教材里的说法。官方不用一个笼统的名词，而是**按具体错误类型逐条写明后果**。以非法地址访问为例，官方原文是：

> 设备在执行加载或存储指令时遇到了**无效的内存地址**。这会让进程进入**不一致的状态**，之后**任何** CUDA 工作都会返回同样的错误。要继续使用 CUDA，**该进程必须被终止并重新启动**。

更严重的情况（例如设备代码里触发了断言）措辞更强：**设备不能再被使用、所有已存在的分配都失效、要继续使用必须终止并重启进程**。

**注意官方给的应对方式是"终止并重启进程"**，而不是"销毁上下文后在同一个进程里重建继续用"。**这一点对上层设计有直接影响**：[L7](../L7-分布式与集群/00-集群是什么.md) 里 checkpoint 机制之所以必需，一部分原因正在于此——**恢复的粒度是进程级甚至更大，所以必须能把状态重建出来**。

> 另一个易混的术语：**"context lost（上下文丢失）"在 CUDA 文档中同样不存在**。设备从总线上掉下来这类故障属于驱动与系统管理范畴，不是用户态运行时的错误类型。说"上下文丢失"时应当明确指的是哪一层。

### 工程上的应对

- **在关键节点插入检查**，把异步错误尽早变回同步可见；注意"读取并清除"与"只读取"两类接口的区别（后者不重置错误状态）；
- **把设备状态看作可能整体失效**：恢复策略是"重建 + 恢复状态"，而不是"修复现场"；
- 因此**需要能把状态快速重建**——这就是 checkpoint 机制重要性的来源，它的必要性一部分来自这一层错误模型的约束。
