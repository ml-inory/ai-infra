# 连接与指标：八层怎么扣在一起、每层拿什么验收

> **这份文档解决什么。** [overview.md](overview.md) 是导航，各层的 `00/01` 是分层教材——但它们都是**平铺**的：每层各说各的，层与层的关系只剩下一句"相关"。
>
> 这篇是唯一的**纵向**文档，回答两件事：
>
> 1. **八层之间的连接**：把上层指标写成下层指标的表达式。这是"连接"的定量形式——能代入数字算，才算真的理解。
> 2. **每层指标的可测性与可控性**：哪些指标现在就能算、哪些要仿真、哪些只有真硅才能测。**这是验收的依据。**
>
> **读者定位**：需要判断"这件事能不能做、做到什么程度算合格"的人。不需要读 RTL 与驱动源码。

---

## 零、口径与设计约束

### 本文的写法约定

**优先级从高到低**：**能算 > 能仿真测 > 只能真硅测 > 是设计目标**。每条指标都必须带这个标签，否则读者无法判断它的可信度。

| 标签 | 含义 |
|---|---|
| **【可算】** | 用公开公式与已知参数就能算出来（例如显存带宽、打包良率） |
| **【可仿真】** | 需要仿真或软件环境才能测（例如提交延迟、队列行为、扩展效率） |
| **【需真硅】** | 只有在真实芯片上才能测（例如中断延迟、IOMMU 缺页开销、复位恢复时间） |
| **【设计目标】** | 尚无任何测量手段，只是我们打算达到的值 |

**这条约定是本文最重要的部分。** 在一个"纸上设计"的项目里，**假装什么都测得了是最容易犯的错**——把【需真硅】的项当成已验证，会让整套论证失去可信度。

### 设计约束（本项目的具体化）

连接与指标是普遍的，但**要可测就必须挂到具体设计上**。本项目的约束：

| 项 | 取值 | 说明 |
|---|---|---|
| **芯粒数** | **4 个**（4 芯 NPU） | 一个封装内 |
| **工艺** | **6nm** | 成熟代际，供应链稳定、封装方案多 |
| **互联范围** | **只有芯间（D2D）互联** | **不做卡间互联** |
| **主机接口** | PCIe 端点 | 通过 BAR/MMIO 交付契约（见 [L2](L2-设备可编程模型/00-设备可编程模型.md)） |
| **外存** | HBM（片外） | |

### 四条约束直接决定了后面所有结论

**第一，"不做卡间互联"让 L7 的含义彻底变了。** 原本 [L7](L7-分布式与集群/00-集群是什么.md) 的核心指标是"扩展效率随卡数怎么衰减"，涉及以太网/InfiniBand 组网。**现在没有卡间互联，扩展效率的适用规模就只有这个封装内的 4 个芯粒。**

这带来两个后果，都是好的：

- **L7 从"最不可控的一层"变成"可算的一层"**——域内互联是设计出来的，带宽与延迟都是我们定的，不存在"客户机房网络好不好"这种外部变量；
- **但 L7 的"分布式"含义收窄了**：它现在讲的是**4 个芯粒之间的并行策略**（数据/张量/专家并行怎么在 4 芯上切），而不是集群调度与多租户。

> **这一条要在项目说明里写清楚**，否则读者会以为这是一个能扩到千卡的方案——**它不是**。它是一张单卡，扩展上限是 4 芯。要谈集群，是"多张这样的卡再组网"，而那部分本项目不做。

**第二，6nm 让 SRAM 的账更紧张。** [L0](L0-物理与工艺/00-物理与工艺.md) 里有一条硬事实：**SRAM 面积随节点缩小得比逻辑慢**（实测某些代际 SRAM 相对上一代只有 1.1 倍）。选成熟节点意味着**单位面积上的片上缓存容量不会很宽裕**——这直接决定了 L1 的存储层次设计、乃至 L5 的 tiling 策略。

**第三，只有 PCIe，没有 CXL。** 主机与设备之间是 PCIe 链路，带宽比显存低一到两个数量级（[L1](L1-芯片与硬件/00-芯片与硬件.md)）。所以**"数据尽量留在设备上"不是偏好，而是这个约束下的必然**。

**第四，4 个芯粒但没有卡间互联，使得"芯粒间互联"成为整个设计的性能枢纽。** 它同时是：

- L1 的 D2D 接口设计（物理与带宽）
- L2 契约的一部分（跨芯粒命令怎么表达）
- L7 的并行策略边界（什么样的切分能跑在 4 芯上）

**这三层围绕同一件事，是本文最重要的"连接"之一。**

## 一、八层指标总表

每条指标的四个属性：**定义口径**、**现在能否测**、**谁控制它**、**它主要影响上层什么**。

### L7 分布式与集群（本项目 = 4 芯粒内部的并行与通信）

| 指标 | 定义口径 | 可测性 | 控制方 | 影响上层 |
|---|---|---|---|---|
| **集合通信带宽** | 芯间聚合带宽（GB/s），含实际的 allreduce/allgather 效率 | 【可仿真】靠互联模型 | **L1 的 D2D 设计**（我们定） | 决定并行策略可行性 |
| **通信占端到端时间比** | 通信时间 ÷ 总时间 | 【可仿真】 | L5 的重叠调度 + L1 带宽 | 直接决定扩展效率 |
| **扩展效率** | N 芯吞吐 ÷（单芯吞吐 × N），N ≤ 4 | 【可仿真】 | 综合（通信 + 切分策略） | 卡的有效算力 |
| **故障恢复时间 MTTR** | 出错到恢复可用的时间 | **【需真硅】**（仿真里只能模拟流程） | L3 的复位与重建路径 | 有效算力占比 |
| **加载/排队延迟** | 从请求到开始计算 | 【可仿真】 | L4 调度 | TTFT 的一部分 |

> **注意 MTTR 是唯一标【需真硅】的 L7 指标**——因为复位是硬件行为。仿真里可以验证"恢复流程对不对"，但测不出"要多久"。

### L6 框架与模型

| 指标 | 定义口径 | 可测性 | 控制方 | 影响上层（L7） |
|---|---|---|---|---|
| **TTFT**（首 token 延迟） | 请求到第一个 token，**必须给分位数** | 【可仿真】软件栈 + 算力模型 | L5 的 kernel 效率为主 | 服务 SLA |
| **TPOT / ITL**（token 间延迟） | 相邻 token 间隔，`≈ 1000 ÷ tok/s/用户` | 【可仿真】 | L1 的访存带宽为主 | 交互档位 |
| **吞吐** | tokens/s，**必须绑定精度与输入输出长度** | 【可仿真】 | L5 + L1 | 单卡产能 |
| **算子支持情况** | 必需算子是否齐全 + 回落清单 | 【可算/可仿真】 | L5 的算子实现 | 决定能不能跑 |
| **编译与冷启动时间** | 首次可用前的编译 + 加载 | 【可仿真】 | L5 编译 + L4 加载 | 扩容与重启成本 |
| **KV cache 占用** | 随并发 × 上下文长度增长 | **【可算】**（容量公式） | L1 的容量 + 量化策略 | 可支撑并发 |

### L5 编译器与算子

| 指标 | 定义口径 | 可测性 | 控制方 | 影响上层（L6） |
|---|---|---|---|---|
| **算力利用率**（离峰值 %） | 实测算力 ÷ 峰值 | 【可仿真】需时序模型 | L5 tiling + L1 微架构 | 直接决定 TTFT/吞吐 |
| **访存利用率** | 实际带宽 ÷ 峰值 | 【可仿真】 | L5 布局 + L1 带宽 | decode 阶段的关键 |
| **算术强度** | FLOP ÷ Byte | **【可算】** | **由 tiling 决定**（不是算法固有） | 判断受限类型 |
| **片上占用 / 寄存器** | tile 缓冲与寄存器用量 | **【可算】**（编译产物里就有） | L5 tiling + L1 容量 | 能不能这样切 |
| **指令数 / kernel 数** | 完成同样计算用了多少 | **【可算】**（静态属性） | L5 融合 | 提交开销 |
| **编译时间** | 编译一趟要多久 | 【可仿真】 | L5 编译器 | 冷启动 |

### L4 用户态运行时

| 指标 | 定义口径 | 可测性 | 控制方 | 影响上层（L5/L6） |
|---|---|---|---|---|
| **单次提交开销** | API 到命令入队的时间 | 【可仿真】 | L2 契约 + L4 实现 | 小算子时是主要成本 |
| **队列深度需求** | Little's law：吞吐 × 延迟 | **【可算】** | L2 契约给上限 | 设备会不会断粮 |
| **分配 / 映射延迟** | 分配与建立映射的耗时 | 【可仿真】 | L3/L4 内存管理 | 热路径能不能不分配 |
| **拷贝带宽** | 四种路径分别计 | **【可算】**（带宽上界）+【可仿真】 | L1/L3 | 重叠率的分母 |
| **同步等待 / 隐式同步** | 显式与隐式同步造成的串行 | 【可仿真】靠时间线 | L4 的流模型 | 并行度能否兑现 |

### L3 内核与系统

| 指标 | 定义口径 | 可测性 | 控制方 | 影响上层（L4） |
|---|---|---|---|---|
| **中断与完成延迟** | 设备完成到软件知晓 | **【需真硅】** | L1 中断 + L3 驱动 | 完成可见性 |
| **系统调用开销** | 一次边界往返 | 【可仿真】近似 | L3 UAPI 形态选型 | 提交路径成本 |
| **IOMMU 缺页与映射开销** | 命中/未命中/缺页三档 | **【需真硅】**（仿真只能近似） | L3 地址空间设计 | 迁移抖动 |
| **队列 IOPS** | 队列吞吐 | 【可仿真】 | L2 契约 + L3 驱动 | 喂饱设备 |
| **复位恢复时间** | 复位 + 状态重建 | **【需真硅】** | L1 复位能力 + L3 流程 | MTTR |

### L2 设备可编程模型

| 指标 | 定义口径 | 可测性 | 控制方 | 影响上层（L3/L4） |
|---|---|---|---|---|
| **命令粒度** | 一次提交最少多少工作 | **【可算】**（契约给定） | **我们设计**（不可改） | 提交开销占比 |
| **队列深度上限** | 硬件定死 | **【可算】** | **我们设计** | Little's law 的上限 |
| **doorbell 覆盖量** | 一次通知最多取走多少 | **【可算】** | **我们设计** | 批处理摊薄上限 |
| **描述符效率** | 字节 ÷ 描述符 | **【可算】** | **我们设计** | 搬运开销 |
| **中断聚合范围** | 可配置的聚合区间 | **【可算】** | **我们设计** | 延迟与 CPU 开销的取舍 |
| **能力位与版本** | 可演进空间 | **【可算】** | **我们设计** | 将来会不会被卡住 |

> **L2 这一整层都是【可算】**——因为它是我们自己定的契约。**这是本项目里最"可控"的一层**，也是为什么它值得最先写实（见第七节）。

### L1 芯片与硬件

| 指标 | 定义口径 | 可测性 | 控制方 | 影响上层（L2/L5） |
|---|---|---|---|---|
| **峰值算力** | **必须带精度 + 稠密/稀疏 + 频率条件** | **【可算】** | 微架构设计 | 所有上层指标的分母 |
| **显存容量与带宽** | 带宽可用公式验算 | **【可算】** | L0 的 HBM 选择 | 容量墙与带宽墙 |
| **片上带宽** | SRAM/NoC 带宽 | 【可仿真】 | 微架构 | 会不会"喂不上数据" |
| **D2D 带宽与延迟** | 芯粒之间的互联 | **【可算】**（设计值）+【可仿真】 | **我们设计** | **L7 的一切** |
| **能效** | 实测吞吐 ÷ 实测功耗，**须说明负载点** | **【需真硅】** | 全栈 | 电费与密度 |

### L0 物理与工艺

| 指标 | 定义口径 | 可测性 | 控制方 | 影响上层（L1） |
|---|---|---|---|---|
| **工艺密度 / SRAM 位单元面积** | 看密度而非节点名 | **【可算】**（查工艺平台数据） | 选型 | 片上缓存划不划算 |
| **良率** | 面积 → 良率（负二项模型） | **【可算】**（模型估算） | 面积与缺陷密度 | 成本 |
| **打包良率** | 各芯粒良率之积 × 封装良率 | **【可算】** | 芯粒划分 | 4 芯的可行性 |
| **lane 速率 × 编码效率** | 有效带宽 = 前者 × 后者 | **【可算】** | 选型 | D2D 与 PCIe 带宽 |
| **TDP 与散热** | 设计目标，非上限 | **【需真硅】** 实测功耗 | 全栈 | 部署形态 |
| **成本** | 每颗好芯片成本（含良率） | **【可算】** | 全栈 | 值不值 |

**把【可算】的项加起来：L0 几乎全部、L1 的核心、L2 全部、L3/L4/L5 的一部分。** 这意味着**这个设计的一大半是可以现在就论证的**——这比"什么都得等流片"要乐观得多。

## 二、因果分解：把上层指标写成下层表达式

这是"连接"的定量形式。**每一条都能代入数字算**——算不出来就说明还没理解透。

### 2.1 TTFT（L6）怎么拆

```
TTFT ≈ 排队时间（L4 调度）
     + prefill 计算时间（L5/L1）
     + 提交与启动开销（L4/L3）
     + 首次编译/加载（若冷启动）
```

**prefill 计算时间进一步拆**：

```
prefill 时间 = 输入 token 数 × 每 token 计算量 ÷ 有效算力
其中 有效算力 = 峰值算力（L1）× 算力利用率（L5）
```

**这条链说明**：TTFT 不好时，**要逐项排查是"排队"还是"算得慢"**——两者优化手段完全不同（前者调调度，后者调 kernel）。

### 2.2 TPOT（L6）怎么拆

```
TPOT ≈ 每 token 需要搬运的字节数 ÷ 有效带宽（L1）× (1 − 重叠率)
```

**decode 阶段每生成一个 token 都要把权重读一遍**，所以它本质是访存问题。**提高 batch 能把这次搬运摊薄到多个请求上**——这就是"甜点"存在的原因（[L7 的性能甜点](L7-分布式与集群/01-集群评测.md)）。

### 2.3 扩展效率（L7）怎么拆——本项目最核心的一条

```
扩展效率 = 1 − 通信时间 ×(1 − 重叠率) ÷ 总时间
其中 通信时间 = 每步通信量 ÷ D2D 有效带宽（L1）
```

**在本项目里，这一条是"可算"的**——因为 D2D 带宽是我们定的、并行策略也是我们定的。**给定切分方式与 D2D 带宽，就能算出扩展效率的上限。**

**这条链的三个可调点**：

| 调什么 | 属于哪层 | 效果 |
|---|---|---|
| 提高 D2D 带宽 | L1（设计） | 直接减少通信时间 |
| 提高重叠率 | L5（调度）+ L4（多流） | 把通信藏进计算 |
| 减少每步通信量 | L7（换切分策略） | 从源头减少 |

**这三条对应 [overview.md](overview.md) 的"重叠率"关系**——它是 L5↔L7 的接口，也是本项目里最值得反复算的一条。

### 2.4 吞吐（L6）怎么拆

```
吞吐 = min(算力受限上限, 访存受限上限) × 并发利用率
其中 算力受限上限 = 有效算力 ÷ 每 token 计算量
     访存受限上限 = 有效带宽 ÷ 每 token 访存字节数
```

**取 min 就是 Roofline**——它把"算力受限还是访存受限"变成了两个数比较大小。

### 2.5 单卡产能（L7）怎么拆

```
单卡有效吞吐 = 单芯吞吐 × 4 × 扩展效率（L7）
最终产能     = 单卡有效吞吐 × 卡数 × 集群扩展效率（本项目不做）
```

**注意本项目只做到前一行。** 第二行的"集群扩展效率"依赖卡间互联，**不在设计范围内**——这条边界要写清楚。

### 2.6 成本（L0/L1→L7）怎么拆

```
$/百万 token = 单卡持有成本 ÷（单卡有效吞吐 × 时间 × 利用率）
其中 单卡持有成本 ≈（硅成本 ÷ 打包良率）+ 封装 + 散热改造分摊
```

**这条链把 L0 的良率与 L7 的成本直接连起来了**：良率下降会直接抬高 $/百万 token。这也是为什么"4 芯粒"这个选择需要算良率账——**4 个芯粒的打包良率是乘积**。

### 2.7 一张"分解关系"总图

```
L7 扩展效率 ── 通信时间 ◄── D2D 带宽（L1）
             └ 重叠率   ◄── 调度（L5）+ 多流（L4）

L6 吞吐 ── min(有效算力, 有效带宽)
         ├ 有效算力 = 峰值（L1）× 利用率（L5）
         └ 有效带宽 = 峰值（L1）× 利用率（L5）

L6 TTFT ── prefill 算力 + 排队（L4）+ 提交开销（L4/L3）

L7 成本 ── 硅成本 ÷ 打包良率（L0）+ 封装（L0）+ 功耗（L0）

L4 队列深度 ── Little's law ◄── 队列上限（L2）
```

**读这张图的方法**：任选一个上层指标，沿着箭头往下走，**走到底就是可以改的东西**。

## 三、三类税的流动账

[README](../README.md) 把"税"分成三类。**把每类税对应到具体层，就能回答"该优先优化哪里"**。

### 3.1 数据移动税：最肥的一块

| 出现位置 | 具体形式 | 属于哪层 | 压它的手段 |
|---|---|---|---|
| HBM ↔ 片上 | 每次访存都要跨这层 | L1 | 加片上缓存、提高复用 |
| 片上 ↔ 计算单元 | 数据进矩阵单元的路径 | L1/L5 | tiling 提高复用率 |
| 主机 ↔ 设备 | PCIe 链路搬运 | L3/L4 | 数据留在设备上、重叠 |
| **芯粒 ↔ 芯粒** | **D2D 上的中间结果** | **L1/L7** | **切分策略减少通信量** |
| 跨进程共享 | 拷贝到中转缓冲区 | L3/L4 | dma-buf 零拷贝 |

**本项目的关键判断**：由于只有 4 芯且有 D2D，**"芯粒间搬运"是这一类税里最可控也最值得算的部分**——它不像主机链路那样被物理约束卡死。

### 3.2 控制/同步税：一次操作值多少次计算

| 出现位置 | 具体形式 | 属于哪层 | 压它的手段 |
|---|---|---|---|
| 提交一次命令 | API → 队列 → doorbell | L2/L4 | 加大命令粒度、批处理 |
| 一次中断 | 设备通知主机 | L1/L3 | 中断聚合 |
| 一次系统调用 | 用户态 ↔ 内核 | L3 | UAPI 选型、用户态队列 |
| 一次同步 | 流间依赖、跨芯同步 | L4/L7 | 减少同步点、异步化 |
| 一次内核态往返 | 缺页、映射 | L3 | 预映射、pin |

**量化方式**：`该操作耗时 ÷ 它覆盖的计算量`。**这个比值高，就说明控制税压过了计算本身**——此时唯一的出路是"让一次操作覆盖更多计算"。

### 3.3 抽象税：让它在热路径上消失

| 出现位置 | 具体形式 | 属于哪层 | 压它的手段 |
|---|---|---|---|
| 跨进程传数据 | 中转拷贝 | L3/L4 | dma-buf |
| 虚拟化 | 中介每一次访问 | L3 | SR-IOV 硬件切分 |
| 框架层 | 类型检查、多次拷贝 | L6 | 编译期消除、零拷贝路径 |
| 指针转换 | 用户态地址 → 设备地址 | L3/L4 | SVA / 共享虚拟地址 |

**这类税的特点是"可以完全没有"**——不是减少，而是让它在快路径上不存在。**判断标准**：热路径上一次多余的拷贝都没有。

### 3.4 三类税在本项目的优先级

| 税类 | 本项目的主要矛盾 | 优先级 |
|---|---|---|
| **数据移动** | 芯粒间通信 + HBM 带宽 | **最高**（决定扩展效率） |
| **控制/同步** | 命令粒度与 doorbell 覆盖量 | 中（L2 定契约时就要定好） |
| **抽象** | 只有 PCIe 没有 CXL，主机链路是短板 | 中（靠"数据留在设备上"规避） |

## 四、可控性与可测性：一张决策表

这一节回答"**你能改什么**"与"**你能验证到什么程度**"——**这是 Agent 时代最实用的两张表**。

### 4.1 可控性：谁说了算

| 层 | 可控程度 | 说明 |
|---|---|---|
| **L0** | **低**（选型而非设计） | 6nm 是选的，SerDes 与封装是采用现成方案 |
| **L1** | **高** | 微架构、D2D、存储层次全是我们设计 |
| **L2** | **最高** | 完全是自定义契约（但改一次代价最大） |
| **L3** | **高** | 驱动与 UAPI 形态自选 |
| **L4** | **高** | 运行时 API 自定 |
| **L5** | **高** | 编译器与算子自研 |
| **L6** | **中** | 要接入既有框架（PyTorch），受其约束 |
| **L7** | **中**（本项目内高） | 4 芯内并行策略可控；但没有卡间互联，集群部分不可控且不做 |

**读法**：**L2 最可控、L0 最不可控**。所以设计意图应该集中在 L1/L2/L5，而 L0 是"给定条件"、L6 是"要适配的对象"。

### 4.2 可测性：什么时候能验证

| 阶段 | 能测什么 | 不能测什么 |
|---|---|---|
| **现在（纸面）** | L0 全部、L1 的算力与带宽、L2 全部、L5 的静态属性、L7 的扩展效率上限 | 任何延迟类、任何能效类 |
| **仿真环境** | L4 的提交/队列/流行为、L5 的利用率、L6 的吞吐与 TTFT（模型驱动）、L3 的部分（系统调用、队列 IOPS） | 中断延迟、缺页开销、复位时间 |
| **真硅** | 全部 | — |

**关键结论**：**设计里有一大批指标现在就能论证**（尤其 L2 全部、L1 核心、L0 全部），**但所有"延迟"与"能效"类都要等真硅**。

**这直接决定了项目的诚实表述**：可以说"我们论证了带宽、容量、扩展效率上限、良率与成本"，**不能说"我们验证了延迟与能效"**。

### 4.3 对 Agent 验收的含义

Agent 能产出实现（RTL、驱动、编译器），**但它产出的"性能声明"必须落在上表的可测范围内才有意义**：

| Agent 声称 | 可接受的前提 |
|---|---|
| "这个矩阵单元能达到 X TFLOPS" | 只要给得出**峰值算力计算过程**与**仿真里的利用率**，可以接受 |
| "这个驱动的中断延迟是 Y µs" | **不可接受**——这是【需真硅】项，除非有真硅或明确的替代测法 |
| "这个调度能藏住通信" | 可接受，但要给出**重叠率**与**仿真里的时间线证据** |
| "扩展效率能到 Z" | 可接受，但要给出**D2D 带宽与切分策略的代入计算** |

**这张表比任何代码审查都有效**——它把"看起来合理的声称"和"可以验证的结论"分开了。

## 五、验收清单：把指标变成对 Agent 的尺子

每条指标给**目标值 + 测量方法 + 判定阈值**。目标值需要随设计推进填实，**但"测量方法"与"判定阈值的形式"现在就能定**。

### 模板

```
指标：<名称>
层：L<n>
可测性：【可算】/【可仿真】/【需真硅】/【设计目标】
目标值：<数值>（待填）
测量方法：<具体做法>
判定：达标的判据（不是"差不多"，而是一个可判定的条件）
```

### 已经可以填实的几条（示例）

**算力（L1）**
```
目标值：待定（由微架构决定）
测量方法：矩阵单元数 × 每周期运算量 × 时钟频率，按精度分列
判定：给出的数字必须带"精度 + 稠密/稀疏 + 频率"三要素，缺一不接受
```

**D2D 有效带宽（L1，本项目枢纽）**
```
目标值：待定
测量方法：lane 速率 × lane 数 × 编码效率（注意不能漏编码效率）
判定：必须能与其他层的假设对上（L7 的扩展效率计算要用这个数）
```

**打包良率（L0）**
```
目标值：待定
测量方法：各芯粒良率之积 × 封装良率（4 芯 = 四次相乘）
判定：必须给出缺陷密度与聚集因子假设，不能只给一个百分比
```

**扩展效率上限（L7）**
```
目标值：待定
测量方法：1 − 通信时间×(1−重叠率) ÷ 总时间，代入 D2D 带宽与切分策略
判定：必须同时给出"重叠率假设"与"它是怎么来的"
```

**队列深度需求（L4）**
```
目标值：待定
测量方法：Little's law —— 设备吞吐 × 单任务端到端延迟
判定：算出的需求不能超过 L2 契约给的队列上限，否则设计不闭环
```

> **注意最后一条的判定方式**：它不是"这个数好不好"，而是"**它有没有和下一层的约束冲突**"。**跨层一致性检查，才是"连接"这部分真正的验收方式。**

## 六、跨层一致性检查表

写这套设计时，最容易出的错不是某一层算错，而是**层与层对不上**。下面每一条都是真实存在的耦合点：

| 检查项 | 涉及层 | 不通过的表现 |
|---|---|---|
| L7 的切分策略 × L1 的 D2D 带宽 | L7 ↔ L1 | 算出的扩展效率 < 1，说明这个策略跑不动 |
| L5 的 tile 大小 × L1 的片上容量 | L5 ↔ L1 | tile 放不下，只能缩小 → 复用率下降 |
| L4 的队列深度需求 × L2 的队列上限 | L4 ↔ L2 | 需求超过上限 → 设备注定喂不满 |
| L4 的提交次数 × L2 的命令粒度 | L4 ↔ L2 | 一次提交覆盖的工作太少 → 控制税压过计算 |
| L6 的算子集合 × L5 的算子实现 | L6 ↔ L5 | 有算子没有实现 → 回落到慢路径 |
| L6 的显存需求 × L1 的可用容量 | L6 ↔ L1 | **装不下 → 方案不成立**（这是硬失败） |
| L1 的功耗 × L0 的散热能力 | L1 ↔ L0 | 散热压不住 → 降频 → 前面所有算力白算 |
| L0 的良率 × 4 芯的划分 | L0 ↔ L1 | 打包良率太低 → 成本不成立 |
| L7 的 HBM 容量需求 × L0 的 HBM 供应 | L7 ↔ L0 | 单 stack 容量不够 → 要更多 stack → 封装受限 |

**这张表的用法**：设计推进过程中反复跑一遍，**任何一条不过就说明设计还缺一块**。

## 七、这份文档怎么用

### 7.1 你现在的位置

这份总册是**"连接与指标"的纲**，它把八层的 `00/01` 横向串了起来。**下一步是把它变成可验证的东西**——也就是各层的 `02`：

| 档位 | 状态 |
|---|---|
| **00** 这一层是什么 | ✅ 八层齐备 |
| **01** 怎么衡量 | ✅ 八层齐备 |
| **连接与指标** | ✅ **本文** |
| **02** 我们这一层怎么做 | 🔶 进行中：**[L2 契约设计](L2-设备可编程模型/02-契约设计.md) 已完成**，其余七层待写 |

### 7.2 为什么 02 从 L2 开始

**L2 是唯一"完全由我们定、且下游全部依赖它"的层**：

- 它是【可算】的（不需要等仿真）；
- 它的每个数字都直接约束 L3/L4/L5（队列深度、命令粒度、doorbell 覆盖量）；
- **它定下来之后，L1 才知道要实现什么、L3 才知道要驱动什么。**

而且从 Agent 协作看：**L2 的契约写实了，Agent 才有明确的实现目标**——否则它会自己发明一套寄存器与队列格式。

### 7.3 一条务实的推进顺序

```
L2 契约（先写实，它是锚点）
   ↓
L1 微架构 + D2D 设计（按 L2 的要求实现，同时给 L7 提供带宽参数）
   ↓
L7 并行策略（用 L1 的 D2D 带宽算扩展效率上限，反过来约束 L1）
   ↓
L5 算子与编译（按 L1 的微架构做 tiling，按 L2 的粒度做提交）
   ↓
L3/L4 软件栈（按 L2 的契约驱动，按 L5 的需求提交）
   ↓
L6 框架接入（最后做，因为它依赖前面全部）
   ↓
L0 工艺与成本核账（最后算，因为良率与成本要等面积定下来）
```

**注意 L1 与 L7 之间有反馈**：L1 定 D2D 带宽 → L7 算扩展效率 → 若不够，回头改 L1。**这条反馈回路是本设计的核心迭代，要预留时间。**

### 7.4 与 Agent 的分工

| 谁 | 做什么 |
|---|---|
| **人（你）** | 定 L2 契约、定各层 02 的设计决定、**按本文的指标与判定验收** |
| **Agent** | 实现（RTL、驱动、编译器、算子）、跑仿真、产出测量数据 |
| **本文** | 提供**验收的尺子**与**跨层一致性的检查表** |

**一句话**：Agent 负责把东西做出来，**你负责判断"做出来的东西是否符合这些数字之间的关系"**——而后者正是这份文档存在的理由。
