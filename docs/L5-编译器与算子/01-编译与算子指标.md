# 编译与算子指标：算力利用率与访存

> **这一层在讲什么。** [00-编译器与算子](00-编译器与算子.md) 讲清楚了编译是"分层下降、逐级消掉数据搬运"的过程；这篇回答**怎么判断生成的东西好不好**。
>
> **读法。** 只想知道"概念"，读完 00 就够；要调优算子、判断一个算子实现是快是慢、或者评估编译器的成熟度，再往下读这篇。
>
> **和 L6 的分工。** L6 看的是"整套软栈端到端跑得怎样"（TTFT、吞吐、算子支持情况）；这一层看的是**编译产物本身的质量**——同一个算子，编译出来的 kernel 离硬件峰值有多远。**L6 的端到端指标是本层指标的上层封装**，出了问题要往下追到这里才能定位。

---

## 一、这一层指标的独特之处：编译期属性 vs 运行时结果

其它层的指标基本都是运行时测出来的。L5 不一样，它有一类**在编译期就能读出来的静态属性**——这是调优时最有价值的抓手，因为**不用跑就能看出问题**：

| 类别 | 指标 | 什么时候能知道 |
|---|---|---|
| **静态（编译产物属性）** | 指令数、片上内存占用、寄存器占用、融合后算子数、生成的 kernel 数 | 编译完就知道，不用运行 |
| **动态（运行时结果）** | 算力利用率、访存带宽利用率、实际算术强度 | 必须跑起来测 |

**两者的关系是因果关系**：编译器决定静态属性（怎么切块、融合几个算子、用多少片上内存），静态属性再决定运行时能达到多少利用率。所以调优的路径通常是：

```
运行时利用率不达标
   ↓ 先判断受限类别（算力 / 访存 / 控制）
   ↓ 再回看静态属性（tile 大小对不对、有没有融合、片上内存是否溢出）
   ↓ 改编译器参数或换算子实现
```

## 二、算力利用率与访存利用率

这一层最常用的两个数，和 [overview.md](../overview.md) 的 Roofline 关系直接对应：

| 指标 | 定义 | 典型偏低原因 |
|---|---|---|
| **算力利用率** | 实际达到的算力 ÷ 硬件峰值 | tile 太小/太大、矩阵维度不友好、并行度不足 |
| **访存带宽利用率** | 实际带宽 ÷ 峰值带宽 | 复用率低、布局差、没有重叠 |
| **片上带宽压力** | 片上 SRAM/寄存器的读写次数 | 分块策略差导致片上反复搬运 |

**关键判断规则**：两个利用率**都低**，通常说明不是硬件不行，而是**调度或依赖**出了问题（等待、气泡、启动开销）。这时该看的是重叠率和指令数，而不是继续调 tile。

> L6 里提到的 MFU / MBU 是这两个指标在"整模型"尺度上的说法。这里的区别是**作用对象**：L6 量的是一个模型跑完的整体效率，L5 量的是**单个算子/kernel**离峰值有多远。定位问题时先看 L6 的哪个算子耗时最多，再用 L5 的指标看那个算子为什么慢。

## 三、算术强度：把"受限类型"算出来

```
算术强度 = 计算量（FLOP） / 访存量（Byte）
```

这个模型通常被称为 **Roofline**，出自 Williams、Waterman、Patterson 2009 年的论文（*Roofline: an insightful visual performance model for multicore architectures*，CACM 2009，DOI 10.1145/1498765.1498785）。

算术强度本身不是"好坏的分数"，而是**判断瓶颈类型的工具**——配合硬件的"算力/带宽比"（Roofline 的拐点）使用：

```
拐点 = 峰值算力 / 峰值带宽      （例如 1000 TFLOPS ÷ 3 TB/s ≈ 330 FLOP/Byte）

算术强度 < 拐点  → 访存受限：优化重心是"少搬数据、提高复用率"
算术强度 > 拐点  → 算力受限：优化重心是"提高并行度、用好矩阵单元"
```

**为什么这一层特别强调它**：算术强度**很大程度上由编译器的 tiling 策略决定**，而不是由算法固定。同一段数学，切块方式不同，算术强度可以差几倍——这就是 tiling 值得反复调的原因。

一个实用推论：**decode 阶段是典型的访存受限**（每个 token 要读一遍权重、算量却很小），所以它的优化手段（提高 batch、量化权重、KV cache 优化）和 prefill（算力受限）完全不同。这条规律在 [L6 的 prefill/decode 分测](../L6-框架与模型/01-框架指标.md) 和 [L7 的甜点](../L7-分布式与集群/01-集群评测.md) 里反复出现，根源就在这里。

## 四、片上资源占用：决定"能不能这样切"

tiling 不是想切多大就切多大，**片上存储和寄存器是硬上限**：

| 指标 | 含义 | 超了会怎样 |
|---|---|---|
| **片上内存占用** | tile 缓冲占用多少 SRAM | 放不下就得回落到更小的 tile，复用率下降 |
| **寄存器占用** | 每个线程/单元用多少寄存器 | 超限会"溢出"到本地内存，性能断崖 |
| **占用率（occupancy）** | 资源占用如何限制并行块数量 | 并行度不足，延迟藏不住 |
| **双缓冲开销** | 为了重叠搬运要额外占用的缓冲 | 占用翻倍，可能挤掉更大的 tile |

**这里有一个反复出现的取舍**：tile 越大复用率越高，但片上放不下；为了重叠搬运要双缓冲，缓冲又占掉一半容量。所以 tiling 的调优本质是**在容量约束下最大化复用率**——这也是自动调优要搜索的东西。

## 五、指令数与启动开销

一个常被忽略但很能说明问题的静态指标：**完成同样计算用了多少条指令、启动了多 少个 kernel**。

- **指令数偏多**：说明没有有效利用宽指令（矩阵/向量指令），退化成了逐元素操作。
- **kernel 数偏多**：说明算子没有融合，中间结果反复落 HBM，且每次启动都有固定开销。
- **启动开销占比**：在计算量小的算子上，启动开销可能比计算本身还大（这就是 CUDA Graph 这类机制存在的理由，见 [L6](../L6-框架与模型/00-框架与模型.md)）。

这两个指标的好处是**不需要硬件计数器就能拿到**（编译产物里有），适合做快速回归检查。

## 六、编译时间与搜索成本

这一层还有一类"非性能"指标，但在工程上同样关键：

| 指标 | 为什么重要 |
|---|---|
| **编译耗时** | 影响开发迭代速度；服务场景里变成冷启动的一部分 |
| **自动调优耗时** | 参数搜索可能要跑很多次，首次部署成本高 |
| **调优结果与形状的绑定程度** | 换 batch/序列长度是否需要重搜——决定部署灵活性 |
| **缓存命中率** | 编译/调优结果能否复用，决定扩容与重启要等多久 |

**一个容易踩的坑**：只比较"稳态性能"而忽略"达到稳态的成本"。一个启用了激进自动调优的方案，稳态可能快 20%，但如果每次扩容都要重新搜索几十分钟，实际收益可能是负的。

测量手段可沿用 L6 那几个官方 API（`torch._dynamo.utils.compile_times()`、`TORCH_COMPILE_DEBUG=1`、tlparse），它们分别给出各编译阶段的耗时。

## 七、怎么评测才算可信

**必须固定的**：算子形状（batch、序列长度、hidden 维度）、精度、tile 与并行参数、目标硬件型号与频率状态、以及是否启用了自动调优。

**必须报告的**：算力利用率与访存利用率**两者都给**（只给一个无法判断受限类型）、算术强度、以及芯片频率是否锁定（**不锁频的跑分不可比**）。

**这一层特有的坑**：

- **只测一个形状就下结论**：算子的效率与形状强相关，小矩阵和大矩阵可能相差一个数量级。
- **把 GEMM 峰值当成模型效率**：模型里大量时间花在访存受限的算子上，只看大矩阵乘会高估。
- **忽略 host 侧开销**：kernel 执行很快时，CPU 提交与同步的时间会主导端到端。
- **用未锁频的机器对比不同实现**：频率波动足以掩盖优化收益。
- **把自动调优的峰值当常态**：调优结果绑定形状，换配置就退化。

## 八、一张表：该看哪个指标

| 你要回答的问题 | 该看的指标 |
|---|---|
| 这个算子离硬件峰值有多远 | 算力利用率 + 访存利用率（两者一起看） |
| 它是算力受限还是访存受限 | 算术强度 vs 硬件拐点 |
| 为什么利用率上不去 | 静态属性：tile 大小、片上占用、寄存器溢出、指令数 |
| 融合有没有生效 | kernel 数量、中间结果的 HBM 读写量 |
| 切更大的 tile 行不行 | 片上内存占用与占用率 |
| 部署要等多久 | 编译耗时 + 自动调优耗时 + 缓存命中率 |
| 值不值得开自动调优 | 稳态收益 vs 搜索成本，以及形状绑定的代价 |
