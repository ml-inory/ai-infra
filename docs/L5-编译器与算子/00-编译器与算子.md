# 编译器与算子：把数学变成指令

> **这一层在讲什么。** 上一层交下来的是"一张计算图"（[L6](../L6-框架与模型/00-框架与模型.md)），下一层要的是"一串能提交给设备的指令"（L4 用户态运行时）。中间这段翻译就是 L5：**决定算什么、按什么顺序算、数据放在哪、怎么搬**。
>
> **本文建立概念，不追求精确。** 想知道"编译出来的东西到底多快、怎么量"，看 [01-编译与算子指标](01-编译与算子指标.md)。
>
> **和上下层的关系。** L6 负责"捕获与表达"，L5 负责"怎么变成高效指令"，L4 负责"怎么送进去执行"。**抽象税在这一层被压得最狠**——算子融合、tiling、布局变换都是在消掉"本可以不发生"的搬运和启动开销。往下还压不动的东西（比如数据必须搬进片上存储），就交给 L1/L2 用硬件解决。

---

## 一、这一层到底在解决什么

把"翻译"这件事拆开，L5 每天面对的是三个决定：

| 决定 | 问题 | 做不好会怎样 |
|---|---|---|
| **算什么** | 哪些算子能合并、哪些必须分开 | 中间结果反复读写，带宽白烧 |
| **数据放哪** | 放在 HBM、片上 SRAM、还是寄存器 | 容量不够或带宽不够，算力空转 |
| **怎么搬** | 什么时候搬、搬几次、能不能与计算重叠 | 算力等数据，利用率掉下去 |

**这三个决定没有独立最优解**，只能一起权衡——这就是编译器存在的理由，也是它难以完美自动化的原因。

### 与"传统编译器"的根本差别

| | 传统编译器（CPU） | AI 编译器（NPU/GPU） |
|---|---|---|
| 主要矛盾 | 指令级并行、分支预测 | **数据搬运**（每算一个 FLOP 要搬多少字节） |
| 程序形态 | 通用控制流 | 以数据流图为主，形状已知 |
| 优化空间 | 相对成熟、有几十年积累 | 巨大且依赖形状/布局，**搜索空间爆炸** |
| 性能瓶颈 | 指令发射、缓存命中 | 片上容量、访存带宽、并行度切分 |

一句话：**传统编译器主要跟控制流较劲，AI 编译器主要跟数据搬运较劲。** 记住这条，后面所有技术都能对上位置。

## 二、编译是分层下降的过程

一次完整的编译不是"一步到位"，而是**从抽象到具体的逐级下降**，每一级只负责消掉一类开销：

```
高层算子树（L6 交下来的计算图）
    ↓  图级优化：算子融合、常量折叠、布局变换
图 IR（算子变少、变小）
    ↓  循环级优化：tiling、double buffering、软件流水
循环 IR（明确"分几块、搬几次、怎么重叠"）
    ↓  指令生成：指令选择、片上内存分配、寄存器分配
设备指令流（交给 L4 提交）
```

**为什么要分层**：因为不同层次的优化互相干扰。上层关心"少做点事"，下层关心"把事做得更满"。混在一起做会陷入局部最优——这也是为什么各家都选择用多层 IR（中间表示）来表达，而不是一个大 pass 通吃。

**这套做法的标准化成果是 MLIR**（Multi-Level IR）。它用 **dialect（方言）** 机制解决"不同层次、不同厂商共存"的问题：每个 dialect 有独立命名空间，可以定义自己的算子、属性和类型，**多个 dialect 能共存于同一个模块里，并由 pass 在不同 dialect 之间转换**。这正好对应上面的分层需求——高层 dialect 表达张量计算，低层 dialect 表达循环与向量，两者之间的下降由一组可复用的 pass 完成。

官方给出的**上移理由**，恰好说明 AI 编译器为什么不能沿用传统编译器的分工（原文大意）：

> 神经网络加速器有处理大块数据的专用单元，它们的计算要映射到**不止一层循环**上。让一个工作在接近汇编的低层 IR 上的后端去"抬起并重建循环"再做这种映射，是困难甚至不可行的。这与今天传统编译器中的指令选择与调度形成对比——**后者主要只处理最内层循环的循环体**。

这句话很值得记住：**传统编译器管最内层循环体，AI 编译器要管"多层循环怎么映射到专用单元"**。这也解释了为什么向量化、软件流水这类决策在 AI 编译器里被上移到了中高层 IR。

## 三、图级优化：少做点事

目标很直接——**减少算子数量、减少中间结果、减少数据搬运**。

| 优化 | 在做什么 | 收益来源 |
|---|---|---|
| **算子融合** | 把相邻算子合成一个 kernel | 中间结果不进 HBM，省带宽 + 省启动开销 |
| **常量折叠** | 编译期把能算的算完 | 运行时少算 |
| **布局变换（layout）** | 把数据改成硬件喜欢的排布 | 让后续算子能走高效路径 |
| **死代码消除** | 去掉无用计算 | 少算 |

**算子融合是收益最大的一项，也最值得理解。** 它的本质是：两个算子串行执行时，第一个算子要把结果写回 HBM，第二个再读回来——这一写一读可能比计算本身还贵。融合之后中间结果留在片上，这段搬运就消失了。

融合有不同的层次：把逐元素操作链合成一个（最常见）、把归约操作与其前后处理合并（epilogue fusion）、把多个消费者共享的中间结果只算一次。**融合的边界由内存容量和依赖关系共同决定**，不能无限融。

## 四、循环与调度：把事做得更满

算子和搬运都确定了之后，还有一个关键问题：**怎么切分、怎么排顺序**。

### 4.1 Tiling（分块）

片上存储（SRAM / 寄存器）容量有限，HBM 带宽也有限。Tiling 就是**把大张量切成能装进片上存储的小块**，一块算完再算下一块：

```
问题：算 C = A × B，但 A、B、C 都远大于片上存储
做法：按块（tile）迭代，每轮只取需要的分块进片上，算完写回
关键：块的形状与顺序决定"每块数据被复用多少次"
```

**Tiling 的核心指标是数据复用率**：同一个数据块从 HBM 搬进片上后，能被用几次。复用率越高，单位数据带来的计算越多，越接近算力上限——这正是 Roofline 模型里"算术强度"的来源。官方文档把这条理由说得很直白：**更大的 tile 意味着更少的全局内存访问，从而保证 DRAM 带宽不成为瓶颈**。

**Tiling 不是一层，而是多层。** 以 GEMM 库的官方实现为例，一个矩阵乘会被映射成**三层嵌套的 tile**，分别对应并发的三个层级和存储层次的三级：

```
threadblock 级 tile  ←  从全局内存装载，对应"块间并发"
      ↓
warp 级 tile         ←  从共享内存取到寄存器，对应"块内并发"
      ↓
thread 级 tile       ←  寄存器内累加，寄存器不共享
```

**越往右越细，越靠近计算单元。** 这种"多层 tiling 对应多层并发 + 多层存储"的映射思路是通用的——换任何加速器，本质都是把同一件事按它的并发模型和存储层次重做一遍。

### 4.2 重叠：让搬运藏起来

即使 tile 切得再好，"搬数据"和"算数据"仍是两件事。如果串行执行，带宽和算力就轮流闲置。于是：

- **Double buffering（双缓冲）**：准备两块缓冲，一块在算、一块在搬，交替进行——**把搬运时间藏进计算时间**。
- **软件流水（software pipelining）**：把循环的不同迭代错开排布，让加载、计算、写回三个阶段流水线化。

**为什么必须做这件事，官方文档给了定量理由**：累加器本身就要占掉每个线程**至少一半的寄存器预算**，因此占用率（occupancy）天然偏低，GPU 隐藏访存延迟的能力受限。既然"靠并行度自动隐藏延迟"这条路走不通，就必须**显式地用软件流水去重叠**——在共享内存层面开两块 tile 缓冲，在寄存器层面开两份数据片段。

这个理由值得记住：**当硬件资源被算法结构挤占时，重叠就不能指望自动发生，必须由编译器显式安排**。这也是为什么 tile 大小、流水级数这些参数需要按硬件搜索——它们之间是硬的资源约束关系。

更进一步的形态是把不同角色拆给不同的执行单元（例如一组专门负责搬运、一组专门负责计算），以及让不同数据块的计算与写回互相重叠。这些都属于同一目标：**让任何时刻都没有空闲的单元**。

> 前面提到的重叠率关系（[overview.md](../overview.md)）在这里落地成具体手段：**通信/搬运时间 ×(1 − 重叠率) 必须能被计算时间盖住**，否则那个环节就是瓶颈。

## 五、后端代码生成：落到具体硬件

到了这一层，抽象已经很低，做的是三件传统编译器也在做、但对象不同的事：

| 阶段 | AI 编译器里的对应物 |
|---|---|
| 指令选择 | 把循环 IR 的运算映射到硬件指令（矩阵乘/向量指令/访存指令） |
| 内存分配 | **片上内存分配**——SRAM 用哪块、双缓冲怎么切、寄存器怎么分 |
| 调度 | 指令排布，兼顾流水线、访存延迟隐藏与依赖 |

**这一层是"硬件差异"最集中的地方**：不同 NPU 的片上存储层次、DMA 引擎、矩阵单元接口都不一样，所以后端往往是厂商自研、且不开源的部分。这也是为什么"换一块卡要重新调"——上层图优化可以通用，后端的 tiling 参数与指令映射必须重做。

## 六、算子库与自动调优

不是所有东西都交给编译器生成。**高频且结构固定的操作（矩阵乘、卷积、注意力、归一化）值得专门优化**。业界分成两条互补的路：

### 6.1 手写模板库：把 GEMM 做到极致

以主流的 CUDA C++ 模板库为例，它的官方定位是"**一组用于实现高性能矩阵乘及相关计算的抽象，涵盖各种层级与规模**"，且是 **header-only 模板库**（不需要预先编译）。

它的价值不在"提供几个 kernel"，而在于**把 tiling、数据搬运、流水线这些 L5 的核心概念做成了可组合的抽象**。上一节那套三层 tiling 就是它的标准做法。后来的版本还引入了专门描述"布局与张量"的 C++ 抽象，官方称这些布局**可以通过函数式组合来操纵，并在此基础上构建 tiling 与分块等常见操作**——这等于把 L5 的调度决策暴露成了一套组合子。

**配套还有一个重要现象**：这类库会提供 profiler，**把厂商闭源库的结果作为对照打印出来**（同一个 GEMM 两套实现对比）。这说明"手写模板库 vs 厂商库"不是替代关系，而是**互相验证、按形状各自取胜**的关系。

### 6.2 面向深度学习的原语库

另一条线是把深度学习常用操作封装成"深度学习版的 BLAS"——这个类比有明确出处：**BLAS 在 HPC 领域解决的是基础线性代数的高效实现，而深度学习缺少对应的库**，于是诞生了 cuDNN 这类**面向深度学习工作负载、意图与 BLAS 类似的优化原语库**。

分工可以这样理清：

| 库 | 定位 |
|---|---|
| BLAS 类（cuBLAS） | 基础线性代数原语 |
| 深度学习原语库（cuDNN） | 面向深度学习工作负载的优化原语，意图与 BLAS 类似 |
| 模板库（CUTLASS） | header-only 的 C++ 模板抽象，用来**自己搭**高性能 kernel |

国产侧同样有对外的算子开发接口（例如昇腾 CANN 的 Ascend C，官方文档以 API 参考形式提供，含 SIMD API、基础 API 等分类）——**这类接口是厂商把"怎么写高效算子"开放给开发者的入口**，也是判断一个生态成熟度的实际指标。

### 6.3 DSL：让编译器替你做调度

手写库的问题是"只能覆盖常见形状"，而编译器从零生成又常常打不过手写。第三条路是**用一门受限的 DSL 描述 tile 级计算，把调度交给编译器**：

- **Triton** 的官方定位是"一门并行编程语言与编译器"，目标是让人能用 Python 写出接近硬件峰值的自定义 kernel。它的关键设计是**改变了并行模型**：传统 CUDA 是"**标量程序、阻塞的线程**"（每个线程算一个标量，靠线程块协作），Triton 是"**阻塞的程序、标量线程**"（每个程序实例直接操作一整块 tile）。
- 这个转变带来的是**编译器可以自动完成原本要专家手写的调度**：自动合并访存、线程重排、预取、向量化、面向张量核心的指令选择、共享内存分配与同步、异步拷贝调度。
- 它与 PyTorch 编译栈的关系是明确的：**TorchInductor 在 NVIDIA 与 AMD GPU 上以 Triton 作为核心构造块**——也就是说，你在 L6 用 `torch.compile` 时，GPU 上生成的多半就是 Triton kernel。

**学术侧的对应工作**也是同一思路：TensorIR 把循环嵌套表示推广成"以张量计算为一等公民"，自动调度器则用"从分层搜索空间采样 + 进化搜索 + 学习到的代价模型"来搜最优程序。

### 6.4 自动调优的代价

不管哪条路，tile 大小、展开次数、流水深度这些参数组合都多到无法手调，只能**在目标硬件上自动搜索**并缓存结果。这带来一个工程副作用值得记住：

**自动调优的结果与具体形状绑定。** 换一个 batch size 或序列长度，可能需要重新搜索——所以"首次运行的编译/调优时间"在服务场景里是真实成本（见 [L6 的编译与冷启动](../L6-框架与模型/01-框架指标.md)）。

## 七、算法级重写：当编译器也救不了

有些问题不是"编译得不好"，而是**算法本身与硬件的访存模式不匹配**。这时要在算法层面重写——最典型的例子是 **FlashAttention**（论文 [arXiv:2205.14135](https://arxiv.org/abs/2205.14135)）。

它提出的核心原则是 **IO-aware（访存感知）**：设计算法时要**把 GPU 各层存储之间的读写次数算进去**，而不只看计算量。标准注意力会把中间矩阵完整写回 HBM 再读出来，而这个矩阵的大小随序列长度**平方**增长，于是访存成为瓶颈。FlashAttention 用 **tiling** 减少 HBM 与片上 SRAM 之间的读写次数，论文进一步分析了它的 IO 复杂度，证明它**在一系列 SRAM 容量下都是最优的**。

它值得单独记住的原因是方法论的示范：

- **它不是近似算法**——论文标题里的 "Exact" 就是这个意思，收益完全来自访存优化，不来自牺牲精度；
- **它证明了"把数据留在片上"这个 L5 的核心思想可以上移到算法层**。很多推理优化（KV cache 量化、分块处理、算子重排）都是同一思路的不同体现；
- 它的续作（FlashAttention-2，[arXiv:2307.08691](https://arxiv.org/abs/2307.08691)）把重点放在**并行度与工作划分**上：减少非矩阵乘的 FLOP、让单个 head 跨 thread block 并行、减少 warp 间的共享内存通信——**当算法已经 IO 最优之后，下一个瓶颈就变成了并行度**。

一个有用的量化感受：论文报告第一版只达到理论峰值 FLOPs 的 **25–40%**，第二版提升到 A100 上的 **50–73%**。**同一套数学、同一个访存原则，并行策略不同就能差出一倍**——这正是 L5 存在的意义。

## 八、低精度与稀疏

两种"少算一点"的手段，都会改变编译器的做法：

### 8.1 低精度：编译器要管"量化算子放哪"

低精度不只是在算子内部换数据类型，它还会引入一批**表示量化与反量化的算子**，而它们的摆放位置决定了性能：

- 一种做法是让量化后的算子自带量化语义（**算子导向**：量化版的卷积、整数矩阵乘等各有自己的定义）；
- 另一种做法是在原算子之间**插入"量化→反量化"对**（**张量导向**），用它们来模拟量化过程。后者的一大好处是：**编译器知道"这里曾经模拟过量化和反量化"，于是可以自由地把这些转换算子移动到更划算的位置**——这正是编译器能发挥作用的地方。

**融合在这里的作用**也被官方说得很具体：把一个卷积和紧随其后的批归一化**先融合成一个算子，再对它做量化，效率会高得多**。换句话说，**图优化做得好，量化才能做得干净**。

两个层次的术语要分清：

| 阶段 | 含义 |
|---|---|
| **训练后量化（PTQ）** | 直接量化已训练好的模型；需要**校准数据**来统计激活分布，校准方法常见有按极值、按熵、按分位数 |
| **量化感知训练（QAT）** | 在训练过程中模拟量化误差，让模型"适应"低精度——前两种达不到精度目标时的最后手段 |

> **术语警告**："量化"在业界**没有统一定义**。有的项目把它限定为"8 位线性量化"，有的（如 MLIR）明确说自己覆盖的范围"相当窄"、不是通用参考。所以看到"我们支持量化"时，要问清是哪种。

### 8.2 稀疏：结构化换硬件可用性

稀疏的动机是跳过零元素，但**零的分布方式决定了硬件能不能真的省下时间**：

| 类型 | 零的分布 | 硬件可用性 |
|---|---|---|
| **非结构化稀疏** | 任意位置 | 理论省算力，但硬件难以高效利用（不规则访存） |
| **结构化稀疏** | 固定模式 | 硬件有专门通路，能真正加速 |

**最有说服力的证据来自硬件本身**：主流 GPU 从某一代起在矩阵单元里引入了稀疏支持，采用的正是 **2:4 模式（50% 稀疏，即 4 个元素中保留 2 个）**，官方论文明确其效果是**相对稠密矩阵单元把数学吞吐翻倍**（[arXiv:2104.08378](https://arxiv.org/abs/2104.08378)）。

**这就是取舍的量化形式**：结构化换来的是"硬件真的能加速 2 倍"，代价是**压缩率上限被锁死在 50%**——非结构化理论上可以压得更狠，但拿不到硬件加速。所以"哪种稀疏更好"取决于你能不能让权重适配这个固定模式。

编译器侧也在跟进：MLIR 有专门的稀疏张量 dialect 与一篇同行评审论文讨论其支持（*Compiler Support for Sparse Tensor Computations in MLIR*，ACM TACO 2022，DOI 10.1145/3544559）；而在库侧，稀疏 MMA 也已作为一等能力出现在模板库里。

## 九、一条重要的术语警告

写这一层的材料时会遇到几个**看起来通用、其实各家定义不同**的概念，跨项目直接等同会出错：

| 概念 | 实际状况 |
|---|---|
| **算子覆盖率** | **没有权威统一定义**。分母（算子粒度、是否含融合算子、是否按形状计）和统计方法（按算子个数还是按算力加权）都没规定。用之前必须自定义口径 |
| **算子融合的分类** | 也**没有统一分类法**。不同项目各用各的：有的用"横向/纵向融合 + epilogue 融合"，有的只讲 epilogue，有的按结构化算子加 tiling/fusion pass 来讲 |
| **"指令选择 / 寄存器分配"在 AI 编译器里的对应物** | **没有权威统一说法**。可以核实的是：MLIR 明确把向量化与软件流水这类低层调度**上移到中高层 IR**，理由是加速器的专用单元处理的是"跨多层循环"的数据块，而传统编译器的指令选择与调度**主要只处理最内层循环体** |

**这条警告本身就是一个知识点**：这一层是"厂商自定义"最重、标准化最弱的一层，所以**文献里的术语必须带着项目名去理解**。
