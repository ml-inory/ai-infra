# 设备可编程模型：硬件与软件的契约

> **这一层在讲什么。** 前面几层讲的都是"怎么把设备用起来"（驱动、运行时、框架）；这一层往下一层，讲的是**设备本身向软件承诺了什么**：它有哪几种寄存器和窗口、命令怎么写进队列、设备怎么通知你算完了、数据怎么搬。
>
> **理解这层的最好方式是把它当成一份"契约"**：硬件承诺"你按这个格式写，我就按这个语义执行"，软件承诺"我不会越界、会按约定维护这些结构"。**契约定得不好，后面所有层都要跟着付代价**——这也是为什么这一层是整个技术栈里"一旦流片就无法修改"的部分。
>
> **本文建立概念，不追求精确。** 想知道"一次提交最少要多少工作量、队列要开多深"，看 [01-设备契约指标](01-设备契约指标.md)。
>
> **和上下层的关系。** 往下，这份契约由 [L1 的硅](../overview.md)实现；往上，[L3 的驱动](../L3-内核与系统/00-内核与系统.md)负责认领设备并把它翻译成系统能用的对象，[L4 的运行时](../L4-用户态运行时/00-用户态运行时.md)则沿着这份契约做高频提交。

> **说明**：一个仓库只能引用公开资料来讨论这一层。真实的 NPU 契约大多是保密的，所以本文**用公开的成熟接口作为范例**（virtio、NVMe、PCIe 能力结构），它们把同样的设计问题处理得很干净——**看懂了这些，再看任何私有契约都能认出其中的套路**。

## 一、一份好的契约要同时满足三件事

| 要求 | 含义 | 做不好的后果 |
|---|---|---|
| **明确** | 每个字段的位置、宽度、语义无歧义 | 厂商各自解读，驱动移植就出错 |
| **高效** | 一次操作的开销尽可能低 | 上层再怎么优化，都无法突破这一层的地板 |
| **可演进** | 能加能力、能兼容旧版本 | 新硬件必须换一套驱动，生态碎片化 |

**这三者天然冲突**：为了明确要多写字段（开销大），为了高效要少写字段（容易歧义），为了可演进要留扩展位（浪费空间）。

成熟接口的做法是**分层**：把不常变的东西（能力、版本）放在"发现阶段"一次问清，把常变的东西（每次提交的命令）压到最紧凑。

## 二、第一个设计问题：命令粒度

**一次提交最少能描述多少工作？** 这是整份契约里影响最深远的一个选择。

```
粒度太粗（一次提交一个大任务）
  → 灵活度差：想跑个小规模的活也得按大任务的框架来
  → 设备内部调度负担重，但提交开销摊得薄

粒度太细（一次提交一个微小操作）
  → 灵活度好：什么形状都能表达
  → 提交开销占比高：设备还没算完，CPU 已经提交不动了
```

**这不是理论担忧**。当单个任务的执行时间降到微秒级甚至更低时，"提交一次"的固定开销就会成为瓶颈——这正是 [L4](../L4-用户态运行时/01-运行时指标.md) 里"提交开销要配工作量看"的根源，而**粒度是契约层面就决定了的**，上层只能靠合并与批处理去弥补。

所以一份契约通常会**同时提供两种粒度**：

- **细粒度通道**：单个算子/单个 kernel 的提交，用于灵活表达；
- **粗粒度通道**：把一串任务打包成一个整体提交（图/任务链），用于摊薄开销。

## 三、第二个设计问题：队列长什么样

命令要通过队列交给设备。**几乎所有的现代设备都用"环形队列"（ring）**，因为它不需要动态分配、天然支持生产者-消费者模型。

最干净的公开范例是 **virtio 的 split virtqueue**：它把队列拆成三个独立的部分，各自的职责非常清楚：

| 部分 | 谁写 | 作用 |
|---|---|---|
| **Descriptor table** | 驱动写 | 描述"这次要搬哪些缓冲区"（地址、长度、方向、是否可以链式） |
| **Available ring** | 驱动写 | 告诉设备"我放进去了哪些描述符" |
| **Used ring** | 设备写 | 告诉驱动"我处理完了哪些，以及结果长度" |

**为什么这样拆**：描述符表是"内容"，两个 ring 是"进度指针"。**设备只读驱动写的部分，驱动只读设备写的部分**，双方各自推进自己的指针——这就是所谓的**单生产者单消费者（SPSC）无锁队列**。

**把这三个部分的实际参数列出来，能看清一个真实契约长什么样**（virtio 1.2 规范原文）：

| 部分 | 对齐 | 大小 | 谁写 |
|---|---|---|---|
| Descriptor Table | 16 字节 | `16 × 队列深度` | 驱动 |
| Available Ring | 2 字节 | `6 + 2 × 队列深度` | 驱动 |
| Used Ring | 4 字节 | `6 + 8 × 队列深度` | 设备 |

**队列深度必须是 2 的幂，上限 32768**。描述符是一个固定 16 字节的结构（地址 8 字节 + 长度 4 字节 + 标志 2 字节 + 下一个描述符索引 2 字节），三个标志位分别表示"链式继续"、"这是设备可写区"、"这是间接描述符表"。

**这些数字本身就说明了契约的设计取向**：

- **对齐要求各不相同**（16/2/4）——因为访问模式不同：描述符要按项随机访问，ring 只需要顺序推进；
- **大小是"固定头 + 数组"**——那个 `6` 就是头部（标志位 + 索引），后面才是环形数组；
- **深度上限是硬编码的**，所以"队列能开多深"是契约给定的天花板（对应 [01 的队列指标](01-设备契约指标.md)）。

### 进度索引与"谁拥有这一项"

让这个设计成立的机制是**两个索引**：驱动侧的可用索引与设备侧的使用索引。它们环回前进，**两者之间的区间就是"设备该处理但还没处理"的部分**。规范对索引有一条硬约束：**驱动侧的索引只能递增、不能回退**（回退会破坏"这一项归谁"的判断）。

> 这正是**背压（backpressure）**的天然来源：如果设备处理不过来，可用索引会追上使用索引，队列满，驱动只能等——不需要额外的流控协议。

**NVMe 用的是同一套思路的另一种表达**：它把队列分成**提交队列（SQ）**和**完成队列（CQ）**两个独立环，提交队列项 64 字节、完成队列项 16 字节（规范把这两个尺寸作为"必需值"规定下来），各自解决"我要你做什么"和"你做完了"两件事。

**这类设计的两个要点值得记住**：

1. **队列项的格式是固定宽度的数组**，不是链表。这样可以按索引直接定位，不需要遍历，也不涉及内存分配。
2. **"谁拥有这一项"必须无歧义**。队列里每一项在任意时刻要么属于驱动、要么属于设备，靠索引指针划分边界。**这个所有权约定是整份契约里最容易出错的地方**，也是需要内存屏障的原因（见第七节）。

**NVMe 用的是同一套思路的另一种表达**：它把队列分成**提交队列（SQ）**和**完成队列（CQ）**两个独立环，各自解决"我要你做什么"和"你做完了"两件事。

## 四、第三个设计问题：怎么通知设备（doorbell）

队列在内存里，设备不会自己去轮询（轮询浪费功耗和带宽）。所以需要一种轻量的通知机制：**软件往一个特定寄存器写一个值，表示"队列里多了新内容"**。

这个机制叫 **doorbell（门铃）**。**它在 Linux 内核驱动源码里有明确的一手定义**，不是纯口头说法：

> AMD 的 KFD 驱动把 doorbell 描述为"一个 PCI MMIO 区域，接收 32 位写入并作为队列的写指针（wptr）传递"，并说明**它就是给用户态应用写队列用的**；Intel 的 Xe 驱动则把它定义为"让用户态应用**无需每次提交都陷入内核**就能向硬件提交工作的机制"。

这两句定义合起来，正好点出 doorbell 的本质：**它是把内核从高频提交路径上摘出去的那个装置**。

它有几个设计要点：

- **写入的值通常不是"新命令的内容"，而是"进度指针"**（例如"我的生产者索引到 5 了"）。设备自己从队列里取内容——**通知只传指针，不传数据**，这是它轻量的原因。
- **写入是 posted write**：软件写完就继续干活，不等设备确认。所以**单独测这个写操作没有意义**，有意义的是"通知到完成的往返"（见 [01](01-设备契约指标.md)）。
- **队列和 doorbell 是成对出现的**：有几个队列就有几个 doorbell（或 doorbell 数组的下标），这样多队列可以并行、可以绑到不同 CPU 核。

**真实规范里的 doorbell 长什么样**（NVMe over PCIe 规范原文，能看清这套机制的全部细节）：

```
提交队列 y 的尾指针 doorbell：偏移 0x1000 + (2y)   × (4 << DSTRD)
完成队列 y 的头指针 doorbell：偏移 0x1000 + (2y+1) × (4 << DSTRD)
```

三个细节都值得注意：

1. **主机写"尾指针"，设备写不了头指针**——主机报告"我提交到哪了"（提交队列尾），也报告"我处理到哪了"（完成队列头）。**完成队列的"设备写到哪了"则由完成项自己携带**，不需要额外通知。
2. **步长是可配置的**（`DSTRD` 字段）：等于 0 时每个 doorbell 占 4 字节，否则按 2 的幂放大。**这是为将来扩展预留空间的做法**——不改地址布局就能加宽寄存器。
3. **规范明确要求"主机不应读取 doorbell 寄存器"**，读回的值是厂商自定义的。**这印证了 doorbell 是纯单向的"发信号"通道，不是状态查询接口**——状态要从别处（完成项、状态寄存器）读。

> **一次通知覆盖多少工作是这套机制的关键参数**：规范里，两次尾指针写入之间的差值就表示"这次往队列里加了几条命令"。所以**一次 doorbell 覆盖的条目数是由软件决定的，但上限受队列深度约束**——这直接对应 [01 里"doorbell 覆盖量是摊薄上限"](01-设备契约指标.md)。

> 术语提醒：**CUDA 官方文档并不使用 "doorbell" 这个词**，有的运行时（如 Level Zero）用 Command Queue / Command List 这套说法。**同一件事在不同厂商文档里叫法不同是常态**，按语义理解即可。

**一个反向设计也值得知道**：有些场景下软件会主动去读设备的状态寄存器（轮询完成），而不是等中断。这是**用 CPU 换延迟**——轮询能拿到最低延迟，代价是占满一个核。低延迟推理里这种做法并不罕见。

## 五、寄存器与窗口：控制面与数据面分开

设备的寄存器通常分成两类，**这个分离是刻意的**：

| 类别 | 内容 | 访问频率 |
|---|---|---|
| **控制寄存器** | 配置、启动、复位、模式设置 | 低（初始化、状态切换） |
| **状态寄存器** | 设备状态、错误、计数器、完成进度 | 中（轮询或诊断） |
| **数据通道** | 队列、doorbell、DMA 描述符 | **高（每次提交）** |

**为什么要分开**：控制面访问往往要序列化、要检查权限、可能有副作用；数据面访问必须尽可能便宜。把它们混在同一段地址里，硬件就无法针对高频路径做优化。

**访问宽度是个真实的坑**：很多设备的 MMIO 只接受特定宽度的访问（例如只接受 32 位对齐的读写）。用错宽度可能**读到全 1、或者产生未定义行为**，而且不会报错——表现为"驱动上去没反应"。这类约束通常在设备手册里明确写出。

**"窗口（aperture）"机制**解决的是地址空间不够用的问题：设备内部可见的地址空间远大于分配给它的 BAR 区间，于是用一个**窗口寄存器**来切换"当前这段 BAR 映射的是设备内部哪一块"。访问不同区域要先改窗口寄存器的值——**代价是访问不连续区域时需要来回切换**，这会破坏批量访问的效率。

## 六、DMA：数据怎么搬

命令只是"让设备做什么"，数据还得真的移动。设备通过 **DMA** 直接读写主机内存（不占用 CPU），描述这件事的结构叫 **DMA 描述符**。

描述符要表达的信息基本固定：

| 信息 | 说明 |
|---|---|
| **地址** | 数据在哪（可以是设备地址，经 IOMMU 翻译——见 [L3](../L3-内核与系统/00-内核与系统.md)） |
| **长度** | 搬多少 |
| **方向** | 读还是写 |
| **链式标记** | 是否指向下一个描述符（支持分散聚集） |

**"分散聚集（scatter-gather）"是关键能力**：数据在物理内存里往往不连续，描述符链让设备能一次搬运多段不连续的内存，而不需要软件先做一次大拷贝把它拼起来。**没有这个能力，零拷贝就无从谈起**。

> **真实的描述符格式有两种典型取向**：virtio 用一个**统一的 16 字节描述符**（地址/长度/标志/下一个），简洁但每项表达力有限；NVMe 则提供两套——**PRP**（简单物理页列表，适合常规场景）与 **SGL**（分类型的段描述符，表达力更强，是否支持由控制器能力字段声明）。**这个对比说明描述符格式是在"简单"与"表达力"之间取平衡**：简单的格式硬件好实现，复杂的格式能表达更多数据布局。

### 完成语义：两种"怎么知道数据可见了"

设备把数据写进内存后，软件怎么知道"数据已经可见、可以读了"？**这是描述符契约里最容易被忽略、也最容易出错的部分**，而真实规范给了两种截然不同的答案：

| 方案 | 机制 | 代表 |
|---|---|---|
| **靠软件屏障** | 规范要求在更新"进度索引"前后插入屏障；硬件不额外提供顺序保证 | virtio 的 split 队列 |
| **靠硬件位翻转** | 设备每次投递完成项时**翻转**一个标志位；软件维护"本地期望值"，读出来一比对就知道这条是不是新的 | NVMe 的 Phase Tag |

**NVMe 的 Phase Tag 值得展开，因为它把同步问题消掉了**：

```
主机初始化时：把该队列所有完成项的 P 位统一设为 0，并记住"我期望 P = 0"
设备投递新完成项：把这一项的 P 位翻转为 1（即与上次相反）
队列回绕一圈后：整体再翻转一次，期望值随之更新
```

**主机只需要比较"读到的 P"与"我期望的 P"**：相等说明这是新完成的项，不等说明这个槽位还是上一轮的残留。**没有计数器需要原子更新，没有额外的同步原语**——顺序问题被编码进了一个位里。

规范还规定：**如果一条完成项是由多次写入构造的，P 位必须在最后一次写入时才更新**。**这就把"P 位可见"变成了"整条完成项都已写好"的发布点**——这是这套机制的完整含义。

**为什么这件事值得记住**：它是"**用协议设计消除同步需求**"的漂亮样本，也说明了这一层设计质量如何影响上层——**如果契约把这个责任推给软件，那每个驱动都要自己保证对，而且很难验证**。

  这里有两种在真实规范里都能看到的解决思路，**它们体现的是两种不同的哲学**：

  | 思路 | 做法 | 实例 |
  |---|---|---|
  | **靠屏障（软件负责）** | 规范要求软件在关键点插入屏障，明确"谁先谁后" | virtio 的 split 队列：规范原文一律是"**一个合适的屏障**"——放置描述符与 ring 之后、更新索引之前必须屏障，读通知抑制标志之前也必须屏障 |
  | **靠位翻转（硬件负责）** | 设备每次投递完成项时**翻转**一个标志位，软件靠它与本地期望值比较来判定"这条是新完成的" | NVMe 完成队列的 **Phase Tag** 位 |

  > **一个必须纠正的常见误会**：**virtio 里没有叫 "FENCE" 的标志位**。有人（包括我在起草这份文档时）会以为它用"屏障位"来表达内存序——**实际规范全文都只有"a suitable memory barrier"这种措辞**，是**对软件的要求**，不是硬件里的一个字段。真正的"flag 位"式设计出现在 virtio 的 packed 队列与 NVMe 的 Phase Tag 上。
  >
  > 这个区别很重要：**"屏障位"意味着硬件能替你保证顺序，"要求软件插屏障"意味着顺序责任在驱动侧**——两者对驱动开发者的要求完全不同。

> 一个实用判断：**凡是"设备写内存、软件读"的机制，都要问一句"顺序怎么保证"**。回答不清楚，就会有偶发的、极难复现的数据错误。

## 七、中断与完成通知：靠中断还是靠轮询

设备完成工作后要通知软件，两条路：

| 方式 | 特点 |
|---|---|
| **中断** | CPU 不空转，但通知有延迟、有处理开销 |
| **轮询** | 延迟最低，但 CPU 一直占用 |

**现代设备大多用 MSI/MSI-X**：设备直接向一个特定地址写数据来触发中断，好处是不共享中断线、**支持多个向量**。

**"多个向量"为什么重要**：一条中断可以对应一个队列，于是：

```
队列 0 的中断 → CPU 核 0
队列 1 的中断 → CPU 核 1
   ↓
中断处理天然并行，不会全挤在一个核上
```

**中断聚合（coalescing）是这一层的标准配置项**：设备可以攒够 N 个完成事件、或者等固定时间再发一次中断，以此降低 CPU 开销。**代价是单事件的可见延迟变大**。所以这一层通常提供配置接口，让上层按场景选（高吞吐选高聚合，低延迟选低聚合甚至轮询）。

**完成通知与完成队列是两件事**：完成队列是"记录结果的地方"，中断（或轮询）是"知道有新记录的机制"。有的设计还支持**把完成通知写到另一个队列**，让软件按自己的节奏处理，而不是被中断打断。

---

## 八、能力发现与版本兼容

设备不是一块死板的东西：同一系列可能有不同功能、不同版本、可选特性。**软件必须先问清"你这块有什么能力"，再决定用哪套流程。**

主流的做法是**能力位（capability bits）+ 协商**，公开范例：

- **PCIe 的能力结构**：设备把"我支持哪些扩展能力"组织成一个**链表**，软件从头遍历，逐项读取。这样设计的好处是**旧软件遇到不认识的能力可以直接跳过**，而不是解析失败。
- **virtio 的 feature bits**：设备和驱动各自声明支持的特性集合，取交集之后才使用——**只有双方都支持的特性才启用**。这是向后兼容的标准套路。

**三条实践规律**：

1. **能力用位图表达**，不用版本号硬编码；
2. **双方协商取交集**，而不是"要么全用新特性、要么退回老模式"；
3. **不认识的位直接忽略**，让扩展性不依赖软件升级。

**版本号的作用与直觉不同**：它主要用来**标记"语义发生不兼容变化"**，而不是"功能多少"。功能多少由能力位表达——**这两个维度分开，才能既加功能又不破坏兼容**。

---

## 九、这份契约里最难的三个取舍

1. **粒度**：细粒度灵活但开销高，粗粒度高效但表达力弱。成熟方案是**同时提供两条通道**。
2. **通知方式**：中断省 CPU 但有延迟，轮询延迟低但吃 CPU。成熟方案是**可配置的聚合策略**（并且这一层的选择权交给上层）。
3. **内存序**：全加屏障最安全但最慢，不加屏障最快但可能出错。成熟方案是**只在不变量上要求屏障**（例如 virtio 只对两处指针推进要求屏障）。

**它们共同的形状是**：契约层面不替使用者做决定，而是**把选择权下放，并把每种选择的语义定义清楚**。

---

## 十、这一层是"不可修改的部分"

最后一件事值得强调：前面几层都可以打补丁、换实现、升级版本，**只有这一层的错误是无药可解的**。

- 寄存器语义定错了 → 所有驱动都要写绕过代码；
- 队列格式定得不合理 → 上层永远有一块性能损失；
- 忘了留扩展位 → 下一代硬件必须换一套接口，生态分裂；
- 内存序没定义清楚 → 偶发数据错误伴随整个产品生命周期。

所以这一层的设计质量，**直接决定了这整个技术栈能达到的上限**。
