# 设备契约指标：粒度、队列与描述符

> **这一层在讲什么。** [00-设备可编程模型](00-设备可编程模型.md) 把这一层讲成一份硬件与软件之间的契约；这篇回答**怎么量这份契约好不好**。
>
> **读法。** 只想知道"概念"，读完 00 就够；要做选型、要判断"性能上不去到底是软件没写好还是契约本身不行"，再往下读这篇。
>
> **这一层指标的独特之处**：它们大多是**契约决定的固定成本**，软件改不动。所以看这些指标的目的往往不是"怎么优化"，而是**"还剩多少空间可优化"**——先确认天花板在哪。

---

## 一、把指标分成两类：契约定的 vs 软件调的

这是理解本层指标的关键框架：

| 类别 | 例子 | 谁能改 |
|---|---|---|
| **契约决定** | 命令最小粒度、队列最大深度、doorbell 一次覆盖多少、描述符宽度、MSI-X 向量数 | **改不了**（除非重新流片） |
| **软件可调** | 实际提交批次大小、队列用多深、聚合参数、轮询还是中断 | 运行时与驱动 |

由此得到一个很有用的判断方法：

```
某项开销如果"怎么调都降不下来"  → 说明撞到了契约地板
                                   该问的是"能不能换一条通道"（例如改用图提交）
而不是继续在同一维度上调参
```

**这一层的指标几乎都是在量"地板有多高"。**

---

## 二、命令粒度：地板的最直接体现

| 指标 | 含义 |
|---|---|
| **最小工作单元** | 一次提交最少能描述多少工作（一个算子？一个 kernel？一个任务链？） |
| **单次提交开销** | 组装命令 + 写队列 + 敲 doorbell 的总固定成本 |
| **提交开销占比** | 单次提交开销 ÷ 单次实际计算时间——**这个比值决定上限** |
| **粒度比** | 一个"上层工作单元"需要多少次设备提交（例如一个 Transformer 层需要几次 launch） |

**怎么用它下判断**：

```
提交开销占比 << 1  → 提交路径不是瓶颈，去查设备和算子（L5）
提交开销占比 ≈ 1   → 提交路径就是瓶颈，且多半撞到了契约地板
```

**第二种情况下的唯一出路是换粒度**：把多个细粒度命令打包成一次粗粒度提交（图/任务链）。这不是"优化"，而是**换一份子契约**——而且**前提是契约提供了这条通道**。如果契约只给了细粒度通道，那就真的是天花板。

**粒度比也解释了框架层的行为**：为什么编译器要拼命做算子融合（[L5](../L5-编译器与算子/00-编译器与算子.md)）？**因为融合直接减少了提交次数**——省下的不只是访存，还有每个 kernel 的固定开销。

---

## 三、队列：深度与所有权

| 指标 | 含义 | 注意 |
|---|---|---|
| **队列最大深度** | 队列能容纳多少未完成的条目 | **硬件定死**，是硬上限 |
| **可用深度** | 扣掉保留槽位后实际能用的深度 | 有些契约会强制留空位以区分"空/满" |
| **队列数量** | 支持多少条并行队列 | 决定并行度上限与中断分发的粒度 |
| **队列的内存占用** | 每条队列占多少主机内存 | 队列多了会显著吃内存 |

**"可用深度"这个细节值得知道**：环形队列的经典问题是"头和尾相等时是空还是满"。常见解法是**牺牲一个槽位**来区分这两种状态——所以"最大深度 256"的实际可用可能是 255。契约里通常会写明这一点。

**队列深度够不够，用 Little's law 反推**（和 [L4](../L4-用户态运行时/01-运行时指标.md) 里是同一个关系）：

```
最低需要深度 ≈ 设备消费速率 × 单任务端到端延迟
```

如果算出来的需求超过契约给的最大深度，**说明这条队列注定喂不满设备**——要么用多条队列，要么减少单任务的延迟。

**队列是共享资源**：多进程/多虚拟机时，深度要分。所以"每条队列多深"在虚拟化场景下是个分配问题，不只是技术参数。

---

## 四、doorbell：覆盖量决定摊薄上限

这一层有个特别重要的指标，它直接给"批处理能省到多少"设了上限：

```
doorbell 覆盖量 = 一次通知，设备最多能取走多少工作
```

**为什么它这么关键**：即使软件攒了一大批命令，**如果一次 doorbell 最多只能让设备取走 N 项，那这批命令就要敲多次门**。也就是说：

```
实际通知次数 ≥ 命令总数 ÷ doorbell 覆盖量
```

**这是硬件决定的摊薄上限。** 软件能做的是"把每次通知都用满"（不要让设备一次只取走一项就等着），但**不能突破覆盖量本身**。

**另外要区分两个量**：

| 概念 | 含义 |
|---|---|
| **doorbell 覆盖量** | 一次通知能让设备取走多少（硬件行为，可能不公开） |
| **软件批量大小** | 软件一次攒多少命令再发（软件可调） |

**诊断信号**：如果软件已经把批量开到最大、但通知次数仍然降不下来，那就是撞到覆盖量了——**这不是调参能解决的，只能等下一代硬件**。

## 五、DMA 描述符：效率与表达能力

| 指标 | 含义 |
|---|---|
| **描述符大小** | 每个描述符占多少字节（固定，硬件定死） |
| **单描述符最大传输长度** | 一条描述符最多描述多少字节 |
| **字节/描述符** | 实际平均一条描述符搬了多少数据——**越大越省** |
| **是否支持分散聚集** | 能否用描述符链表示不连续内存 |
| **描述符开销占比** | 描述符本身的内存与处理开销 ÷ 实际搬运的数据 |

**最关键的判断是"字节/描述符"**：

```
数据被切得越碎 → 需要的描述符越多 → 每个描述符都要被写、被读、被处理
              → 描述符开销可能超过数据搬运本身
```

**分散聚集能力直接决定零拷贝可不可行**（见 [L3](../L3-内核与系统/00-内核与系统.md) 的 dma-buf）：没有它，不连续的内存必须先被拼成连续块，**那次拼接拷贝就是纯损失**。

**一个常见误区**：把"描述符数量"当成性能指标。真正要看的是**描述符数量与实际搬运数据量的比例**——搬同样的数据用更少的描述符就是进步。

---

## 六、完成通知：可见性与聚合

完成这件事要分两层看，**混在一起会误判**：

| 层面 | 指标 | 含义 |
|---|---|---|
| **完成可见性** | 软件多久能确知"设备写的数据已经可以读" | 受内存序与屏障要求影响 |
| **通知方式** | 轮询间隔 vs 中断延迟 | 两种极端，可配置 |

**内存屏障是有代价的**，但它是正确性的前提（[00 的第六节](00-设备可编程模型.md)讲了原因）。所以契约的做法通常是**只在不变量上要求屏障**，把代价限在最小范围。**评估契约时该看的是"必须加屏障的点有几个"**——点越少，契约越干净。

**中断聚合度**（见 [L3](../L3-内核与系统/01-内核与系统指标.md)）在这一层是设备侧的配置能力：

```
聚合度高 → 中断次数少、CPU 省，但单事件可见延迟大
聚合度低 → 及时，但 CPU 开销高
```

**关键是这一层提供了多大的配置范围**：如果契约允许从"每个完成都中断"到"攒 N 个或超时"全覆盖，那上层就能按场景选；如果只能固定一种，那这一层的适用场景就被限定了。

**轮询与中断的选择权**也很重要：低延迟场景愿意烧一个 CPU 核去轮询。**如果契约不提供轮询完成的方式，那就拿不到最低延迟。**

## 七、能力与版本：演进成本

这类"软指标"在选型时反而很关键：

| 指标 | 含义 |
|---|---|
| **能力位数量与粒度** | 有多少可选特性，粒度是"整块"还是"逐项" |
| **协商机制** | 是取交集、还是"全有或全无" |
| **未知位的处理** | 遇到不认识的能力位是**忽略**还是报错 |
| **保留字段比例** | 命令/描述符里留了多少位给将来用 |

**"未知位忽略"是向后兼容的核心**：新硬件加了能力位，老软件直接跳过继续跑。如果契约规定"遇到未知位报错"，那每次硬件升级都要同步升级软件——**生态会被自己的契约卡住**。

**保留字段比例**像是浪费，其实是**买保险**：现在留几个字节，将来就不用新增一条命令格式（那会破坏兼容）。

## 八、怎么评测才算可信

这一层的评测和别处不同——**目标是量出地板，而不是比谁快**。

**必须固定的**：设备的固件/微码版本、队列配置（深度、数量、绑定关系）、聚合参数、精度与数据布局。

**必须报告的**：契约给的**上限值**（最大深度、覆盖量、描述符宽度）与实际达到值的对比。

**这一层特有的坑**：

- **拿软件优化后的数字当契约能力**：报"每秒 X 万次提交"时，要说清这是软件攒批之后的结果，还是契约本身能支持的。
- **忽略"可用深度"**：把标称深度当可用深度，会算出错误的队列需求。
- **把描述符数量当效率**：要看字节/描述符。
- **不区分中断与轮询的成绩**：两者的延迟量级不同，混在一起没有可比性。
- **忽略固件版本**：同一硬件不同固件的队列行为可能不同。
- **只看稳态、不看启动与复位**：契约里初始化流程的复杂度（要写多少个寄存器、要等多少次握手）直接影响 [L3 的复位恢复时间](../L3-内核与系统/01-内核与系统指标.md)。

## 九、一张表：该看哪个指标

| 你要回答的问题 | 该看的指标 |
|---|---|
| 提交开销是不是瓶颈 | 提交开销占比 = 单次提交开销 ÷ 单次计算时间 |
| 还有多少优化空间 | doorbell 覆盖量 × 队列深度（两个硬上限） |
| 队列够不够深 | Little's law 反推的最低深度 vs 契约最大深度（注意可用深度） |
| 数据搬运效率高不高 | 字节/描述符；是否支持分散聚集 |
| 能不能做到零拷贝 | 分散聚集能力 + dma-buf 支持（跨层看 L3） |
| 延迟能不能压到最低 | 是否支持轮询完成；中断聚合的配置范围 |
| 正确性风险在哪 | 必须加内存屏障的点有几个；完成标志与数据的顺序约定 |
| 将来会不会被卡住 | 能力位粒度、未知位是否忽略、保留字段比例 |
